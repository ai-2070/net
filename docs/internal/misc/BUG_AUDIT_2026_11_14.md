### BUS-01 — Cancelled shutdown cannot be resumed

- **Severity / status:** High; source-confirmed control-flow defect, not runtime-reproduced.
- **Evidence:** `net/crates/net/src/bus.rs:1388-1455` permanently changes `shutdown` from false to true and makes every later caller wait only for `shutdown_completed`. The winning future then awaits producers (`1497-1533`), the scaling monitor (`1571-1573`), drain workers (`1576-1606`), batch workers (`1628-1631`), and adapter operations (`1644-1652`) before publishing completion (`1735`). There is no cancellation guard or independently owned shutdown task.
- **Trigger:** Keep an `Arc<EventBus>`, begin `shutdown_via_ref()`, then drop/abort that future at a pending await (for example an application-level timeout). Invoke shutdown again.
- **Consequence:** No caller can take over the remaining teardown. Subsequent calls time out after the fixed wait, and completion never arrives. Cancellation before `drain_finalize_ready` is published can leave drain workers parked; cancellation after taking worker handles can detach workers while bus-owned senders remain open.
- **Repair direction:** Give teardown an independently owned task and shared terminal result, so callers may cancel their wait without cancelling teardown.
- **Duplicate check:** Focused search of earlier bug audits and code reviews found related shutdown fixes, but no matching cancellation-safety finding.

### BUS-02 — Adapter shutdown failure becomes success for later callers

- **Severity / status:** Medium; source-confirmed.
- **Evidence:** `net/crates/net/src/bus.rs:1650-1652` retains the adapter's inner `Result`; `1734-1736` sets `shutdown_completed = true` and returns that result even when it is `Err`. The losing-CAS path at `1438-1455` returns `Ok(())` as soon as that flag is true. The public completion documentation at `1747-1749` instead says “success path only.”
- **Trigger:** `Adapter::shutdown()` returns an error before its timeout. A concurrent or subsequent caller invokes `shutdown_via_ref()`.
- **Consequence:** The first caller receives the failure, but other callers receive success for the same teardown. `is_shutdown_completed()` also reports true despite its success-only contract.
- **Repair direction:** Store and replay a shared terminal outcome; distinguish teardown-finished from teardown-succeeded in the completion contract.
- **Duplicate check:** Earlier review `CODE_REVIEW_2026_05_01_BUGFIXES_7.md` CR-25 covers premature success on the waiting deadline, not loss of the first caller's terminal error.

### BUS-03 — Explicit flush errors are silently discarded during shutdown

- **Severity / status:** Medium concern; discarded result source-confirmed, concrete built-in-adapter data-loss scenario not established.
- **Evidence:** `net/crates/net/src/bus.rs:1644-1649` checks only the outer timeout result with `.is_err()`. `Ok(Err(adapter_error))` is neither propagated nor logged; even an elapsed flush timeout is only logged. The final return comes solely from `adapter.shutdown()` (`1650-1652`, `1736`). `net/crates/net/src/adapter/mod.rs:166-175` defines explicit flush as persistence of buffered data and also asks shutdown to flush pending data.
- **Trigger / consequence:** A flush operation fails, followed by a successful shutdown. The explicit flush failure disappears from the API and logs. Data loss depends on whether that adapter's shutdown successfully repeats the failed persistence work; it is not proved here.
- **Repair direction:** Inspect both timeout and inner flush results, preserve diagnostics, and define whether a successful shutdown supersedes an earlier flush failure.

### BUS-04 — Scale-down timeout races stranded flush against a detached worker

- **Severity / status:** High; source-confirmed race, not runtime-reproduced.
- **Evidence:** `net/crates/net/src/bus.rs:827-830` removes the shard and captures stranded ring events. At `862-901`, timed-out drain/batch handles are detached, but their sequence mirror is still read and used for a new stranded batch at `919-938`. The detached batch worker can continue receiving queued batches and flushing (`2346-2410`); each future flush obtains its sequence from worker-local state, then publishes the updated mirror (`net/crates/net/src/shard/batch.rs:350-375`). Loading the mirror does not reserve the stranded batch's sequence range.
- **Trigger:** Scale down a shard with both stranded ring events and older batches queued/in progress. Slow adapter operations, enough queued batches, or retries keep the worker alive beyond its `2 × adapter_timeout` join bound. The stranded flush uses the current mirror before the worker forms its next queued batch.
- **Reachability detail:** Finalization observes an empty ring but does not wait for already-selected producers (`net/crates/net/src/shard/mapper.rs:1285-1320`). An ingest that captured the old shard before draining can still enqueue before `remove_shard` captures the stranded ring (`net/crates/net/src/shard/mod.rs:730-745`); there is no shard-local retirement check.
- **Consequence:** The stranded batch and a later detached-worker batch can use the same `sequence_start`. On JetStream their message IDs collide and distinct events can be deduplicated away; even without dedup, newer stranded events can overtake older queued events.
- **Repair direction:** Do not independently dispatch a stranded batch while the old worker may still allocate sequences. Preserve one owner for ordered draining and sequence allocation through the timeout path.
- **Prior related finding:** `BUG_AUDIT_2026_05_03.md` item 28 marks this pattern fixed in the **add-shard rollback** path. This finding concerns the current **remove-shard** path, which still dispatches after timeout.

### BUS-05 — Late producer can successfully enqueue into a removed shard

- **Severity / status:** High; source-confirmed race, not runtime-reproduced.
- **Evidence:** `net/crates/net/src/shard/mod.rs:730-745` resolves and retains a routing-table snapshot before taking the shard lock, then pushes without revalidating membership. `remove_shard` drains under that lock (`1128-1135`) but releases it before publishing the table without the shard (`1137-1160`). `Shard::try_push_raw` (`180-216`) has no retired/closed state. The old table keeps the removed shard object alive.
- **Trigger:** Producer P selects an active shard and retains its old table, then pauses before locking. Scale-down marks/finalizes that shard, performs the final ring drain and removes it; its drain worker observes removal and exits. P resumes, locks the old shard object, and pushes successfully.
- **Consequence:** Ingestion reports success, but neither the new routing table nor any remaining drain worker will visit that ring. The accepted event is silently lost when the stale table/shard is released.
- **Repair direction:** Mark the shard retired under the same shard lock as the final drain, and make writers reject/re-resolve that state before accepting data. A table swap alone does not quiesce snapshot holders.
- **Duplicate check:** The May 18 phase-3 bus/shard review discusses stale snapshots in an add-shard, self-healing scenario (F-5); it does not establish safety of late writes after remove-shard's final drain.

### PERSIST-01 — Empty retention compaction resets sequence allocation on restart

- **Severity / status:** High; source-confirmed by PersistenceAudit and parent source checks; not runtime-reproduced.
- **Evidence:** `net/crates/net/src/adapter/net/redex/file.rs:155-156` derives `next_seq` solely from the last recovered index entry, defaulting to zero. Retention publishes only surviving entries/timestamps via `compact_to` (`1392-1397`), without an independent allocation watermark.
- **Trigger:** Persist events, evict all of them through retention, then close/reopen before another append.
- **Consequence:** The reopened channel reuses sequence numbers. Resume cursors, tokens and derived-state checkpoints can skip new events or refer to different content under an old sequence.
- **Contract / repair:** The in-memory `tail_signals_lagged_when_all_retained_dropped` witness preserves a nonzero allocation watermark; persist that watermark independently of surviving records, including empty generations.

### PERSIST-02 — Missing timestamp sidecar can trigger destructive empty-log recovery

- **Severity / status:** High; source-confirmed; requires external deletion/corruption of the timestamp sidecar.
- **Evidence:** `net/crates/net/src/adapter/net/redex/disk.rs:1859-1862,1999-2036` rejects even a manifest-selected generation unless `idx`, `dat` and `ts` all exist. With no complete candidate it creates generation 1; the subsequent open cleanup sweeps other generations (`629`). Missing timestamps otherwise have an explicit fallback (`disk.rs:2243-2245`; `redex/file.rs:159-175`).
- **Trigger:** Compact to generation 2 or later, allow predecessor cleanup, lose only the live `ts` file, then reopen.
- **Consequence:** Intact index and payload files are abandoned and then deleted in favor of a new empty generation.
- **Repair direction:** Distinguish committed generations from staging candidates. Recover an optional sidecar or fail closed without replacing/sweeping existing data.

### PERSIST-03 — Append after combined-corruption recovery disappears on next reopen

- **Severity / status:** High; source-confirmed recovery/append ordering; not runtime-reproduced.
- **Evidence:** `net/crates/net/src/adapter/net/redex/disk.rs:514-544` trims a non-monotonic suffix only in memory when checksum filtering already removed entries. The actual index remains unchanged; its writer is reopened append-only (`583-588`). The existing `recovery_seq_trim_is_in_memory_only_after_checksum_drop` fixture (`3182-3250`) establishes surviving in-memory sequences `[0,2]` with the bad suffix still on disk.
- **Trigger:** Recover that combined checksum/non-monotonic corruption, append sequence 3, sync, and reopen again.
- **Consequence:** The old non-monotonic suffix is encountered before the newly appended index entry, so recovery discards the acknowledged new append as part of the suffix.
- **Repair direction:** Durably publish the recovered index/timestamp pair before allowing new appends, preferably in a fresh generation; otherwise reject writes until recovery is committed.

### PERSIST-04 — CortEX accepts an incomplete retained replay as full catch-up

- **Severity / status:** High; source-confirmed.
- **Evidence:** `net/crates/net/src/adapter/net/cortex/adapter.rs:883-925` reads `[resume, head)` after `Lagged` but rejects only an entirely empty result. `RedexFile::read_range` omits evicted entries; the loop does not require the first returned event to equal `resume`, nor check sequence continuity.
- **Trigger:** Append sequences 0–4, retain only 3–4, then create a from-beginning materializer. Tail signals lag; direct catch-up returns the nonempty suffix `[3,4]`.
- **Consequence:** State folds only the suffix and `folded_through_seq` advances to 4. `wait_for_seq(4)` can succeed despite omitted history; the stricter applied watermark cannot cross the missing prefix and applied waits can remain pending.
- **Repair direction:** Check the full expected sequence range before folding catch-up results; surface unrecoverable history loss instead of advancing past it.

### PERSIST-05 — Full live-tail buffer permanently stops a recoverable materializer

- **Severity / status:** High; source-confirmed.
- **Evidence:** `net/crates/net/src/adapter/net/redex/file.rs:1693-1709` handles a full watcher channel by trying to put `Lagged` into that same full channel, then drops the sender. Without an intervening receive, the error is lost and the receiver eventually gets EOF. CortEX unconditionally exits on EOF (`net/crates/net/src/adapter/net/cortex/adapter.rs:863-866`), bypassing catch-up.
- **Trigger:** A producer overflows the live tail buffer while the fold task is busy or unscheduled.
- **Consequence:** After draining buffered events, materialization stops permanently even while its source remains open and the missed events are still readable.
- **Repair direction:** Treat unexpected EOF on an open source as lag and enter continuity-checked catch-up/resubscription. `RedexIndex` already distinguishes this case using `is_closed()`.
- **Qualification:** A receiver racing the second send can make explicit `Lagged` delivery succeed; the no-intervening-receive case still deterministically loses the signal.

### PERSIST-06 — Append can commit after close's final durability barrier

- **Severity / status:** High; source-confirmed lifecycle race.
- **Evidence:** `net/crates/net/src/adapter/net/redex/file.rs:470-475` checks closure before acquiring the state lock and does not recheck inside it. `close` sets closed, disconnects watchers under that lock, releases it, then syncs and returns (`1564-1599`). PersistenceAudit found the same check ordering in the other append/skip mutators.
- **Trigger:** Pause an append after its initial closure check, let close finish, then resume the append.
- **Consequence:** The append succeeds on a closed file after subscribers have been disconnected and after the advertised final sync. With `FsyncPolicy::Never`, no later automatic durability barrier remains.
- **Repair direction:** Recheck closure under the state lock in every mutating path so close and append share a lifecycle linearization point.

### PERSIST-07 — Manager close/reopen can race two independent disk handles

- **Severity / status:** High; source-supported concurrency defect; detailed corruption interleaving not runtime-reproduced.
- **Evidence:** `net/crates/net/src/adapter/net/redex/manager.rs:945-946` removes the map entry before closing the file, allowing `open_file` to construct another disk segment for the same directory while the old one is still closing/appending. The neighboring `close_and_unlink_file` explicitly holds an entry guard for its lifecycle sequence (`958-965`).
- **Trigger:** An old append writes payload bytes but has not written its index record. Concurrent close removes its entry and waits for the append; concurrent reopen recovers the old index and truncates its apparent unreferenced payload tail. The old append then writes its index and reports success.
- **Consequence:** Acknowledged data can reference truncated bytes; the reopened handle also starts with an independent stale index and cached lengths.
- **Repair direction:** Serialize close/removal with reopening through the same per-channel entry guard, retaining exclusive lifecycle ownership until close finishes.

### PERSIST-08 — Checksum recovery misaligns persisted timestamps on the next restart

- **Severity / status:** Medium; source-confirmed.
- **Evidence:** `net/crates/net/src/adapter/net/redex/disk.rs:555-574` rewrites timestamps to include checksum survivors only, while retaining the unfiltered on-disk index. On the next open, `read_timestamps` expects the original index count and rejects the shortened sidecar (`2243-2261`); `redex/file.rs:159-175` then substitutes current timestamps.
- **Trigger:** Corrupt the second payload of a four-record log, recover once, then reopen again without compaction. The existing `checksum_filter_preserves_ts_pairing_on_mid_file_drop` fixture covers only the first recovery.
- **Consequence:** Original ages of surviving events are lost. Repeated restarts can keep resetting their ages and delay age-based retention indefinitely.
- **Repair direction:** Publish the recovered index and timestamps together, or retain original timestamp positions until the index is durably rewritten.

### SDK-01 — Python file context manager suppresses durability failures

- **Severity / status:** High; source-confirmed; not fault-injected.
- **Evidence:** `net/crates/net/sdk-py/src/net_sdk/redex.py:66-74` catches and discards every `RedexError` from `f.close()`. Native close propagates core errors (`bindings/python/src/cortex.rs:1061-1067`); core close already handles repeated closure and performs a fallible final sync (`src/adapter/net/redex/file.rs:1564-1599`).
- **Trigger / consequence:** A persistent file's final sync fails on context exit. The `with open_file_cm(...)` statement reports success although its durability barrier failed.
- **Repair direction:** Propagate close failures; preserve/chaining any simultaneous body exception rather than treating every storage error as harmless idempotence.

### SDK-02 — Stream stop does not stop buffered-batch delivery

- **Severity / status:** Medium concern; behavior source-confirmed, exact intended treatment of fetched events undocumented.
- **Evidence:** `net/crates/net/sdk-ts/src/stream.ts:65-97` checks `aborted` only before poll, then yields the whole response without another check. Python has the same pattern in both iterators (`sdk-py/src/net_sdk/stream.py:89-108,133-156`).
- **Trigger:** Fetch a multi-event batch, stop after consuming the first event, then request another item; or stop while an async poll is pending.
- **Consequence:** Additional events still arrive after stop, including the entire pending response in the second case. Typed/channel wrappers inherit this behavior.
- **Repair direction:** Specify whether stop drains buffered events; for immediate-stop semantics, check after polling and before each yield.

### SDK-03 — Python custom channel parsers receive transport envelopes

- **Severity / status:** Medium; source-confirmed mismatch with the helper's payload-only contract.
- **Evidence:** `net/crates/net/sdk-py/src/net_sdk/channel.py:139-154` wraps scalars/lists and escapes sole-`_value` objects. Custom parsing only removes `_channel` (`157-177,264-272`), whereas default parsing also unwraps once (`282-289`).
- **Trigger:** Publish `42`, `[1,2]`, or `{"_value":42}` to a channel using `parse=json.loads` or a scalar/list validator.
- **Consequence:** Custom parsing gets the `_value` envelope instead of the original payload, yielding wrong types/content or rejecting a valid event.
- **Repair direction:** Decode routing metadata and exactly one transport envelope before serializing the payload for a custom parser.

### SDK-04 — Python slot serialization includes synthetic slots and loses private ones

- **Severity / status:** Medium; source-confirmed from implementation and Python slot semantics; not executed.
- **Evidence:** `net/crates/net/sdk-py/src/net_sdk/channel.py:116-130` iterates declared slot names verbatim with `hasattr/getattr`, without excluding `__weakref__` or resolving per-class private-name mangling.
- **Trigger / consequence:** Publish a slotted object declaring `("value", "__weakref__")`: an active weak reference makes the serialized dictionary contain a non-JSON weak-reference object; otherwise an unwanted field is added. A declared `__value` slot is silently omitted because the stored attribute is name-mangled. Channel publish/batch and node emit paths reuse this conversion.

Control sessions run concurrently (`commands/lifecycle.rs:3058-3076`) and each channel-serve operation independently runs in `spawn_blocking` (`3180-3189`). Startup restores only persisted entries (`3590-3593`).

- **Consequence:** Both live gates can be registered while only one update survives on disk; restart silently loses the other access gate.

### CLI-02 — Blob receives share a truncating staging pathname

- **Severity / status:** High; source-confirmed concurrency/alias hazard.
- **Evidence:** `net/crates/net/cli/src/commands/transfer.rs:759-775` opens the deterministic `<out>.partial` with truncating `File::create`; commit renames that same pathname (`790-805`).

### RPC-01 — Duplex response consumption never replenishes finite credits

- **Severity / status:** High; source-confirmed integration gap.
- **Evidence:** `net/crates/net/src/adapter/net/mesh_rpc.rs:7471-7475` sends the response-window header. `cortex/rpc.rs:8507-8511,8548-8557` creates a semaphore and spends a permit for each response. `DuplexStream::poll_next` returns consumed chunks without issuing a response grant (`mesh_rpc.rs:3394-3408`); its wrapper supplies no grant bookkeeping either.
- **Trigger:** Open duplex with `stream_window_initial: Some(1)`, produce two response chunks, and consume the first.
- **Consequence:** The second chunk stalls even though the caller is consuming responses. The terminal can also stall behind the pump.
- **Repair direction:** Add response-window/grant bookkeeping to the duplex receive half, preserving it across split calls. Unbounded windows avoid the path but do not repair finite-window calls.

### RPC-02 — Remote terminals leave upload credit waiters blocked

- **Severity / status:** High; source-confirmed.
- **Evidence:** Client-stream and duplex grant pumps exit when their grant receiver closes without closing the upload semaphore (`net/crates/net/src/adapter/net/mesh_rpc.rs:6826-6833,7482-7489`). Upload waits acquire that semaphore (`2831-2839,3201-3208`). Terminal dispatch removes pending entries and drops grant senders (`cortex/rpc.rs:9569-9589,9618-9647`).
- **Trigger:** Use `request_window_initial: Some(1)`. Send the initial request; the server rejects or times out without consuming it. Attempt another send.
- **Consequence:** The terminal arrives, but the upload waiter can remain blocked indefinitely. For client-streaming, the outstanding mutable send borrow also prevents reaching `finish()` to observe that terminal.
- **Mitigation / repair:** Explicit cancel-token watchers close the semaphore; ordinary remote termination does not. Propagate terminal/deadline state to send waiters and reject further sends.

### RPC-03 — Failed publication permanently spends upload credit

- **Severity / status:** Medium; source-confirmed pre-publication failure path.
- **Evidence:** `net/crates/net/src/adapter/net/mesh_rpc.rs:2831-2840` forgets the acquired permit before fallible admission signing and initial publish (`2856-2870`). Duplex repeats this ordering (`3201-3208,3225-3240`).
- **Trigger:** With upload window one, lazy admission signing fails or initial publication fails before delivery; retry `send` on the still-`JustOpened` handle.
- **Consequence:** The only credit is already consumed, so retry waits forever; the server never received a call from which to grant replacement credit. Cloning initial headers preserves state but not the spent permit.
- **Repair direction:** Keep the owned permit until publication commits, refunding on preparation/pre-publication failure. Cancellation during partial publication requires a separately defined commit contract.

### RPC-04 — Reopening a stream ID resets only the local sequence lifetime

- **Severity / status:** High; source-confirmed asymmetric-close defect; **related known concern, not wholly new**.
- **Evidence:** `net/crates/net/src/adapter/net/mesh.rs:49740-49754` closes local stream state without a peer lifetime transition. A new stream starts `tx_seq` at zero (`wire/src/session.rs:2498-2511`), while an existing peer receive stream retains its frontier and rejects lower sequences (`wire/src/reliability.rs:1212-1216`). Already-signalled receive boundaries are not reset (`wire/src/session.rs:2638-2657`).
- **Trigger:** Deliver reliable data, close/reopen the same stream ID on one side of the same session, then send again while the other side retains its stream.
- **Consequence:** New packets can be classified as old duplicates and acknowledged without consumer delivery. Local epochs/quarantined grants do not synchronize the remote receive lifetime.
- **Repair direction:** Preserve sequence continuity or introduce a fenced wire-level lifetime transition.
- **Prior evidence:** `SDK_AUDIT_2026_10_11.md:105` already documents unsafe native close/reopen and a higher-level workaround that deliberately keeps the stream open. The audited core API still exposes the underlying behavior. The reopen test cited by the subagent (`tests/three_node_integration.rs:4102-4129`) checks successful send, not successor delivery.

### RPC-05 — First reliable boundary can exclude an earlier reliable send

- **Severity / status:** High; source-confirmed concurrency race.
- **Evidence:** `net/crates/net/wire/src/session.rs:970-982` holds a shared stream lookup while separately reserving sequences and claiming the reliable boundary. Reservation uses `fetch_add` (`3380-3383`); boundary promotion uses a distinct compare-exchange (`2736-2739`). The receiver concedes sequences below the stated boundary (`2659-2662`).
- **Trigger:** A reserves sequence 0 and pauses before promotion. Concurrent B reserves sequence 1, wins boundary promotion, and its packet arrives first.
- **Consequence:** The receiver concedes sequence 0; A's genuinely reliable packet is later dropped as a duplicate. Atomic sequence ranges and a once-only boundary claim do not make their combined transition atomic.
- **Repair direction:** Serialize allocation with first reliable promotion, or combine them into one authoritative admission transition.

### RPC-06 — Reliable descriptor headroom is checked but not reserved

- **Severity / status:** High; source-confirmed concurrent-admission gap.
- **Evidence:** `net/crates/net/src/adapter/net/mesh.rs:50086-50109` checks available retransmit descriptors without reserving them. Admission reserves byte credit/sequences only (`wire/src/session.rs:973-982`); descriptors register after delivery (`mesh.rs:50412-50427`). Full-window insertion evicts an unacknowledged descriptor (`wire/src/reliability.rs:1143-1159`).
- **Trigger:** On a supported reliable stream with `window_bytes = 0` and 32 descriptor slots, concurrently admit two calls of 17 packet-sized events before ACKs free capacity. Each independently sees enough initial headroom.
- **Consequence:** Together they exceed capacity, evicting an unacknowledged packet's retransmit state. If that packet was lost, reliable recovery cannot recover it.
- **Repair direction:** Atomically reserve descriptor capacity at admission and release unused reservations on failure. Whole-call checks protect serialized callers, not concurrent ones.

### RPC-07 — Public duplex pump draining outlives deadlines and cancellation

- **Severity / status:** High; source-confirmed; independent of RPC-01.
- **Evidence:** `net/crates/net/src/adapter/net/cortex/rpc.rs:8627-8648` applies the deadline to handler execution only, then awaits the response pump without a deadline (`8649-8653`). That pump can block on a response semaphore (`8548-8557`). Public cancellation removes its map entry but does not close the pump's cloned semaphore (`8794-8800`).
- **Trigger:** With a response window of one, queue two responses, let the handler return, and withhold further credit.
- **Consequence:** The pump and supervising task can remain alive past the deadline without terminal emission or cleanup. CANCEL also need not unblock the credit wait.
- **Repair direction:** Supervise handler and pump under one deadline/cancellation lifetime; close/abort and join the pump before terminal emission. Protected calls already use a bounded supervisor; this finding concerns the public branch.

### RPC-08 — Completed public duplex calls leak flow-control entries

- **Severity / status:** Medium; source-confirmed.
- **Evidence:** `net/crates/net/src/adapter/net/cortex/rpc.rs:8507-8511` inserts a per-call response semaphore. Completion removes `in_flight` and request senders but not `flow_control` (`8727-8729`). The public CANCEL branch removes it (`8800`), but consuming the server terminal marks a clean close (`mesh_rpc.rs:3409-3425`) and suppresses cancel-on-drop.
- **Trigger / consequence:** Repeatedly complete public duplex calls with finite positive windows and response counts within the granted window. Each completed call retains its key/semaphore until the serving fold itself is dropped.
- **Repair direction:** Remove the exact call's flow-control entry on every public completion path.
