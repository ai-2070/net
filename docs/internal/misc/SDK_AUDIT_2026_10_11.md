Static, read-only audit of every SDK surface, run as nine parallel slices: Rust SDK (core/auth, services), TS SDK, Node napi binding, Python SDK, PyO3 binding, Go + C ABI, browser (`browser-ts` + `leaf`), and cross-SDK parity. Each finding was traced caller → callee and marked CONFIRMED or PLAUSIBLE (one link unverified, named in the finding). No builds or tests were run. The two top Rust-core highs (enrollment PSK leak, unauthenticated org floor) were also re-checked by hand against the source.

**Totals: 99 findings — 0 critical, 13 high, 38 medium, 48 low.**

## Cross-cutting themes

1. **Cancellation and close don't reach the work** — Go streaming RPCs, PyO3 sync streams, Rust `MigrationHandle::cancel`, TS CortEX iterables, browser follower org calls, Node unary serve timeout. Async/blocking edges in every binding.
2. **Unbounded buffers fed by remote peers** — browser `LeafStream`, Node `onStreamData` TSFN queue, RTC bootstrap trickle WS / token map, org floor state.
3. **The Go binding still carries the defect classes the MCP review fixed** (double delete, UAF via finalizer races, thread-local last-error without `LockOSThread`) in groups, meshos, cortex, deck.
4. **Zero means four different things** for timeouts/deadlines across languages (disable / immediate fail / default / busy-loop); see parity findings.
5. **Bindings wrap core directly and drift from `net_sdk`** — `serve_enrollment_auto` semantics, Go `TokenRoots: []` fail-open, Python scope filter widening.
6. **Test harnesses hide glue bugs** — sdk-py tests run against a stubbed `net` module; several `cross_lang_*` fixtures claim language coverage they don't have.

## Suggested order of work

1. Security: #1, #2, #3, Go `TokenRoots` fail-open (parity), browser store-handle exhaustion, RTC bootstrap resource limits.
2. Crashes / memory safety: Go #4, #7, #8 and the meshos/cortex/deck mediums; TS `onStreamData` throw → fatal.
3. Hangs: #5, #6, #9/#10 (one fix pattern in both SDKs), PyO3 GIL-holding methods and sync `close()`, Python MeshOS lock.
4. Parity: pick one meaning for zero timeouts and enforce it at every binding boundary; fix fixture coverage claims.

# Rust SDK core audit — mesh / transport / auth half (`net/crates/net/sdk/src`)

Static, read-only audit. No builds or tests were run. Findings are ranked most severe first.

### [high] A subnet-only, org-only or channel-only ("standalone") link can be redeemed at the Noise enrollment listener for the full bundle, including the mesh PSK
- **Where:**
  - `net/crates/net/sdk/src/enrollment/service.rs:311-351`: `decide` never checks the invite's relations.
  - `net/crates/net/sdk/src/enrollment/bundle.rs:828-880`: `MembershipIssuer::issue` always builds `MembershipBundle::new(receipt, self.psk.clone(), contact)`. Its `check` (`bundle.rs:751`) compares only the issuer.
  - `net/crates/net/sdk/src/enrollment/standalone.rs:5-9`: the docs promise "no PSK is delivered".
  - `net/crates/net/cli/src/commands/enrollment.rs:962-1019`: the CLI mints `vec![Relation::Subnet]` (or Org/Channel) links. These use the same `endpoint`, relay and `enrollment_key`, and are offered into the same ledger that `EnrollmentService::bind` (`cli/.../enrollment.rs:345`) serves.
- **Verdict:** CONFIRMED. The only `Relation::Mesh` check is in `check_channel_offer` (`invite.rs:513`), and it only constrains how the invite is shaped.
- **Problem:** The standalone path (`answer_subnet_redeem` over an existing session) is meant to be the only way to redeem a Mesh-less link. But the link also names the Noise enrollment endpoint, and nothing on that path requires `Relation::Mesh` before the transport PSK is delivered.
- **Failure scenario:**
  1. The operator runs `invite --standalone --subnet X` and gets a bearer link with no device bound to it.
  2. The holder runs `enrollment::redeem::redeem(&invite, &fresh_identity, &intent, ..)` against the invite's endpoint.
  3. If the link is preauthorized, or once the operator approves what looks like a subnet request, the holder receives the mesh PSK, a mesh contact and the subnet leaf.
  4. The result is full mesh admission from a link that was scoped to one subnet. Org-only links have the same problem: the PSK and the org audience secret ship alongside the cert.
- **Fix sketch:** In `decide()`, refuse with `Refusal::Invalid` before `claim` (or refuse in `MembershipIssuer::issue`) unless `invite.relations()` contains `Relation::Mesh`. Optionally also reject a Mesh-less bundle in `MembershipBundle::verify_for`, and add a regression test that redeems a standalone link over the Noise path.

### [high] Any connected peer can grow a node's permanent org revocation state without bound (unauthenticated `serve_org_floor`)
- **Where:**
  - `net/crates/net/sdk/src/org/floors.rs:311-345` (`answer_org_floor`)
  - `:363-418` (`serve_org_floor`, a plain `serve_rpc` with no peer check). It is wired on every node by `net/crates/net/cli/src/commands/lifecycle.rs:3588`.
  - Core: `src/adapter/net/behavior/org_revocation.rs:1977-2003` (`apply_bundle` checks only `bundle.verify()`, which is self-signed) and `:137-167` (`merge_bundle` rows are never pruned).
- **Verdict:** CONFIRMED (spot-checked `answer_org_floor` and `apply_bundle`).
- **Problem:** `answer_org_floor` applies any bundle that verifies under its own `org_id`. An org id is just a public key, so anyone can mint one. Nothing compares `bundle.org_id` to the node's `owner_org()` or to any org it has granted.
  - Core's reasoning (`org_revocation.rs:~255-262`) assumes `apply_bundle` is reachable "only from the adopt ceremony, never from the network".
  - The core adopt path refuses foreign bundles (`ForeignFloorBundle`, `org_authority.rs:922-931`).
  - This SDK service bypasses both.
- **Failure scenario:**
  1. A peer sends fresh `OrgFloorRequest`s. Each carries a bundle of up to 64 KiB (about 1–2k nonzero floors) under a throwaway org key.
  2. Each request rewrites and fsyncs the ever-growing `revocation-state.json` under the cross-process lock.
  3. Every later authority install or restart walks all the rows, taking an exclusive fold write lock per row, as the `merge_bundle` comment describes.
  4. The node also returns signed `Applied` attestations for orgs it has nothing to do with.
- **Fix sketch:** Apply only bundles whose org is this node's owner org, or a grantee org with live grants. Answer `NotMember` otherwise, and add per-peer rate limiting.

### [high] `OperatorEnrollment::revoke(device)` does not stop the revoked device from presenting its own bare `root → device` chain
- **Where:**
  - `net/crates/net/sdk/src/operator.rs:288-318` (`revoke` / `revoke_at` raise the floor keyed on the **device**)
  - `net/crates/net/sdk/src/devices.rs:12-17` (docs say the floor "actually kills access")
  - Enforcement path: `adapters/mcp/src/wrap/delegation.rs:243-258` → `sdk/src/delegation.rs:272-288` (`verify`) → core `identity/token.rs:1169-1171` (`is_revoked` compares `issuer_generation < floor(issuer)`)
- **Verdict:** PLAUSIBLE. Unverified link: whether a deployed device ever presents its own bare one-link chain to a `net wrap` provider rather than only through a gateway key. Nothing in the gate prevents it, since `presenter == leaf == device` verifies.
- **Problem:** Floors are checked against each link's **issuer** only. A bare `root → device` grant has one link, issued by the root, so raising the device's floor never touches it.
  - `enrollment.rs:957-961` already concedes this for renewal ("kills its gateway subtree but not the root-issued grant") and patches only `renew`.
  - The `DelegationGate` gets no such patch.
  - The device also signs its own downstream links and so chooses their `issuer_generation`. A revoked device can therefore mint `device → X` with `issuer_generation = floor` and pass.
- **Failure scenario:**
  1. A device is stolen and the operator runs `mesh.revoke(device)`.
  2. The thief signs the invoke envelope with the device key and presents the bare grant.
  3. The provider admits the call until the grant expires, which can be up to about a year.
  4. Existing tests revoke only gateway chains (`delegation.rs:488-496, 680-690`; `operator.rs:601-636`).
- **Fix sketch:** In the gate (or in `DelegationChain::verify`), also reject when any link's **subject**, or the presenter, has a raised floor. That matches the subject-floor check `renew` already does.

### [medium] Unary org calls with `deadline_ms == 0` run with no deadline, contradicting the documented "facade default"
- **Where:**
  - `net/crates/net/sdk/src/org/call.rs:496-530` (`call_bytes_deadline`), `:608-628` (`call_exported_bytes_deadline`), `:470-473` (`call_bytes` passes 0)
  - The streaming twin applies `DEFAULT_LIFETIME_MS` at `:165-190`.
  - Go binding: `bindings/go/org-ffi/src/lib.rs:953`
- **Verdict:** CONFIRMED (spot-checked: `if deadline_ms > 0 { opts.deadline = ... }`, otherwise `CallOptions::default()` has `deadline: None`).
- **Problem:** The docs say `deadline_ms == 0` means "the facade default", and `DEFAULT_LIFETIME_MS` is documented as "applied whenever a binding seam receives `deadline_ms == 0` … never 'no deadline'". The unary seams skip it, so core waits indefinitely, bounded only by session turnover.
- **Failure scenario:** A provider handler that hangs, while the session stays up, blocks any of these forever:
  - `OrgClient::call`, `call_bytes`, `call_exported`
  - Go `net_org_call` with a context that has no deadline (it runs `block_on` on the calling thread)

  The streaming verbs time out after 300 s in the same situation.
- **Fix sketch:** Map `0` to `DEFAULT_LIFETIME_MS` in both unary `*_deadline` seams, as `streaming_options` does.

### [medium] RTC bootstrap trickle WebSocket: no lifetime bound, no cap on re-upgrades per token, and the default 64 MiB message limit
- **Where:**
  - `net/crates/net/sdk/src/rtc_bootstrap.rs:2040-2133` (`trickle_socket`)
  - `:741-750` (`Attempts::authorize` bumps `socket += 1` with no limit)
  - `:2023-2033` (`get_trickle` sets no `max_message_size` / `max_frame_size`)
  - `:1300-1351` (`BootstrapHandle::shutdown` stops only the accept loop)
- **Verdict:** PLAUSIBLE. The loop's lack of any deadline is traced. The 64 MiB / 16 MiB figures are tungstenite's `WebSocketConfig` defaults, which were not re-read in source.
- **Problem:**
  - After the upgrade, `header_read_timeout` no longer applies. The `socket.recv()` loop ends only on a client close or a candidate the core rejects, not when the attempt expires or completes.
  - Re-upgrading on the same token leaves the earlier sockets running.
  - Upgraded sockets outlive `shutdown` while holding an `Arc<MeshNode>`.
- **Failure scenario:** On a public `any_origin` anchor:
  1. Get a credential from `POST /credential` (limited to 30/min per IP), post one valid offer, and receive an attempt token.
  2. Open N trickle sockets with that token, then go silent.
  3. Every socket stays open indefinitely, and each can make the anchor buffer a text message of up to 64 MiB before it is parsed.
  4. Repeating this per IP exhausts file descriptors or memory.
- **Fix sketch:**
  - Bound the recv loop with an idle deadline and the attempt's ICE deadline, and exit once `bootstrap_attempt_is_live` is false.
  - Set `max_message_size` to a few KB.
  - Close a superseded socket generation.
  - Track connection tasks so `shutdown` aborts them.

### [medium] RTC bootstrap HTTPS listener has no deadline for reading the request body (slow-body slowloris)
- **Where:**
  - `net/crates/net/sdk/src/rtc_bootstrap.rs:1513-1518` (`serve_http` sets only `header_read_timeout`)
  - `:1820-1824` (`post_offer` takes `body: String`)
  - `:1110-1115` (`post_credential`)
  - Contract: the `http_idle_timeout` docs at `:332-339`
- **Verdict:** CONFIRMED. hyper 1.x's `http1::Builder` header timeout covers only the headers. axum's `String` extractor reads up to its 2 MB default with no deadline, and no timeout layer is installed.

The connection is held indefinitely and is never charged against the rate limiter. A few thousand such connections exhaust file descriptors, which is exactly the outage the `http_idle_timeout` docs say is prevented.

  - Add `DefaultBodyLimit::max(64 KiB)`.
  - Add a per-request timeout (`tower_http::timeout::TimeoutLayer`, or `tokio::time::timeout` around `serve_connection`).

### [medium] RTC bootstrap attempt-token map never expires entries
- **Where:**
  - `net/crates/net/sdk/src/rtc_bootstrap.rs:686-768` (`Attempts`, which has no timestamp or sweep)
  - Tokens are minted at `:1869`.

### [low] `Identity::issue_token` panics on any non-zero TTL under one second

### [low] `EventStream` / `TypedEventStream` yield poll errors immediately, never back off, and never end
- **Where:** `net/crates/net/sdk/src/stream.rs:166-170` (the `Poll::Ready(Err(e))` arm). Reached via `Net::subscribe` / `subscribe_typed` (`net.rs`).
- **Verdict:** CONFIRMED for the stream's behaviour. The cost depends on the caller's loop.
- **Problem:** A failed `bus.poll` returns `Some(Err)` without touching `current_interval` or the sleep, and the next `poll_next` re-issues the poll at once. Persistent errors therefore produce an endless, back-to-back sequence of `Err` items. Persistent errors include:
  - `ConsumerError::Adapter` while Redis or JetStream is down, or after `Net::shutdown` (whose docs say outstanding streams "observe the bus as shut down on their next operation").
  - `InvalidCursor`: the cursor is never reset, so every retry fails the same way.
- **Failure scenario:** The idiomatic `while let Some(r) = stream.next().await { if let Err(e) = r { warn!(..) } }` spins a core at 100% and hammers the adapter (and the log) for as long as the outage lasts. The backoff exists precisely to avoid this on the empty-poll path.
- **Fix sketch:** Apply the same doubling and sleep on the `Err` arm. Optionally end the stream (`Ready(None)`) once the bus is shut down.

### [low] `CircuitBreaker`: a stray Closed-admitted call that finishes during Open/HalfOpen corrupts the state
- **Where:** `net/crates/net/sdk/src/mesh_rpc_resilience.rs:870-895` (the `(Err(e), Admission::Closed)` arm)
- **Verdict:** CONFIRMED.
- **Problem:** The bookkeeping keys off the admission-time state, not the current state.

- **Failure scenario:** With slow calls (latency longer than `reset_after`), the breaker oscillates or stays `Open` longer than configured. A successful probe can also close the breaker immediately after a fresh failure re-tripped it.
- **Fix sketch:** On a `Closed` admission, update counters only if `g.state == Closed` at bookkeeping time.

The core's own docs on `BLOB_TREE_MAX_TOTAL_SIZE` cite exactly this `with_capacity` hazard.
- **Fix sketch:** Grow the buffer as chunks arrive, or cap the initial reservation (for example `min(total_size, first_chunk_len * 2)`). Point large blobs at `fetch_blob_stream`.

### [medium] `MigrationHandle::cancel()` makes a concurrent or later `wait()` report success
- **Where:** `net/crates/net/sdk/src/compute.rs:2184-2202` (`cancel`), `compute.rs:2052-2099` (`wait_one_attempt`, "status=None + no recorded failure is unambiguously success"). Core: `src/adapter/net/compute/orchestrator.rs:1676-1697` (`abort_migration_with_reason`).
- **Verdict:** CONFIRMED
- **Problem:** `wait_one_attempt` treats "orchestrator record gone and nothing in `recent_failures`" as success. The comment there lists the synchronous abort paths that bypass the dispatcher, but it misses `cancel()`. `cancel()` calls `orchestrator.abort_migration`, which only removes the record and returns a `MigrationFailed` message. Nothing writes `recent_failures` on this node, because the failure callback fires only when the dispatcher receives an inbound `MigrationFailed`. `cancel()` sends that message to the source and target, not to itself.
- **Failure scenario:** `MigrationHandle` is `Clone`. Task A runs `h.wait().await` while task B calls `h.clone().cancel().await` (for example a user abort or a supervisor timeout). On A's next 50 ms poll, `status()` is `None` and `take_recent_failure()` is `None`, so `wait()` returns `Ok(())`. The caller is told an aborted migration completed. It may then route to the target, which rolled back, or tear down the source.
- **Fix sketch:** In `cancel()` (and in any other local abort), insert `MigrationFailureReason::StateFailed("cancel requested")` into `inner.recent_failures` before or with the abort. Better, keep a per-origin "aborted locally" tombstone that `wait_one_attempt` checks.

### [medium] Stale `StandbyGroup` usage docs tell callers to call `on_event_delivered` by hand, which double-buffers events and replays them twice on promote
- **Where:** `net/crates/net/sdk/src/groups/standby.rs:9-27` (module doc: "Every event deliver: … `group.on_event_delivered(event); // buffer for replay` … The `on_event_delivered` call is manual — SDK doesn't auto-hook"). The code it contradicts is `standby.rs:123-129` and `:139-148`, which auto-install a post-delivery observer, and `compute.rs:1112-1120` (`deliver` fires observers). Also `net/crates/net/docs/COMPUTE.md:304`. Core: `src/adapter/net/compute/standby_group.rs:215-217`, a plain `Vec::push` with no dedup.
- **Verdict:** CONFIRMED (the code path is traced; whether a given user follows the stale doc is the human factor)
- **Problem:** Since the observer fix, `DaemonRuntime::deliver(active, ev)` already pushes `ev` into `buffered_since_sync`. The module docs still show the old manual pairing. The method is still `pub` (only `#[doc(hidden)]`; the item doc says "test-only", but the module doc shown on the module page says the opposite). A caller who follows the module doc pushes each event twice, and the core buffer does not dedup by sequence. The Node binding and the TS SDK docs were updated (`bindings/node/src/groups.rs:606-613`, `sdk-ts/src/groups.ts:428-435`). The Rust module doc and COMPUTE.md were not.
- **Failure scenario:** A counter daemon in a standby group. Following the module doc, the user calls `rt.deliver(active, ev)` and then `group.on_event_delivered(ev)` for 10 events after the last sync. The active fails, and `on_node_failure` promotes a standby, which replays 20 events. The promoted counter reads 20 too high, and the state diverges silently.
- **Fix sketch:** Rewrite the usage block in `standby.rs` and COMPUTE.md to match the TS docs (no manual call). Consider making `on_event_delivered` `pub(crate)` or `cfg(any(test, feature = "testing"))`, or dedup by `(origin_hash, sequence)` in the buffer.

### [medium] `serve_tool_streaming` can silently drop the terminal `Result`/`Error` event, which breaks its documented "every stream ends with a terminal envelope" contract
- **Where:** `net/crates/net/sdk/src/tool.rs:482-492` (contract), `tool.rs:538-566` (the loop calls `sink.send(&event)` with no backpressure). `sdk/src/mesh_rpc.rs:844-851` (`ResponseSinkTyped::send` returns `Ok` after a fire-and-forget send). Core: `src/adapter/net/cortex/rpc.rs:2396-2412` (`RpcResponseSink::send` uses `try_send` on a queue bounded by `STREAMING_PUMP_CAPACITY = 1024` and drops on full). The same file's `ToolWatchHandler` doc (`tool.rs:807-822`) records that the typed sink "lowers to the drop-on-full `RpcResponseSink::send` — silent delta loss" and avoids it for that reason.
- **Verdict:** CONFIRMED
- **Problem:** Each `ToolEvent`, including the terminal one, goes through the lossy sink. If the pump queue is full (the caller withholds flow credit, or the handler produces faster than the pump drains), events are dropped and still counted as sent. If the dropped event is the terminal `Result`, `seen_terminal` is already `true`, so no `missing_terminal` is synthesized. The handler returns `Ok(())` and the stream closes cleanly with no terminal envelope and no result.
- **Failure scenario:** An LLM-backed tool yields more than 1024 `Delta` events from an in-memory buffer to a slow consumer, then `Result`. The middle deltas and the `Result` are dropped. The caller's `RpcStreamTyped` ends with `None` after a truncated delta prefix. Adapters that rely on the documented terminal (`formats/anthropic`, `formats/openai`) see a stream that ended without a result.
- **Fix sketch:** Have the streaming tool wrapper use the raw `serve_rpc_streaming` path with `sink.send_wait(..)` (as `ToolWatchHandler` does), at least for the terminal event. Alternatively, add a backpressured `send_wait` to `ResponseSinkTyped` and use it here.

### [medium] A2A durable store: a `Launched` row whose terminal write is lost holds a capacity slot forever, and the write is never retried
- **Where:** `net/crates/net/sdk/src/mesh_a2a.rs:2560-2580` (terminal hook: `let _ = store.record_terminal(..)`, no retry). `sdk/src/a2a_journal.rs:621-627` (`holds_capacity`: `Launched` is always `true`). `a2a_journal.rs:1872-1897` (`prune` never touches `Launched`). `a2a_journal.rs:2444-2456` (`open` rewrites nothing).
- **Verdict:** CONFIRMED
- **Problem:** The terminal hook bridges to the store with a fire-and-forget spawn and discards the result. Any transient journal failure on that write, such as an `Io` from a full disk or a lock error, or a process exit between the executor finishing and the spawned write running, leaves the row `Launched`. That is fine as a status answer: the store reports it as `Interrupted{outcome_unknown}`. But `Launched` counts against `max_in_flight` indefinitely, prune never removes it, and a restart does not clear it. Only an operator `resolve` frees the slot. This also hits **free** catalog services backed by a journal, because `paid=false` rows go through the same `Launched` state, and every free task in flight at a crash leaks its slot.
- **Failure scenario:** A configured service with `max_in_flight = 2` and a journal. Two tasks complete while the disk is briefly full, so both `record_terminal` writes fail. The live registry shows `Completed`, but the store holds two `Launched` rows. Every later prepare or submit answers `Busy` until an operator notices and resolves both. The `Busy` reply is retryable, so callers retry forever.
- **Fix sketch:** Retry `record_terminal` with backoff inside the spawned task, or re-drive it from the registry's terminal state on the next store write. For `paid=false` rows, `open()` could convert inherited `Launched` rows to `Terminal{Interrupted}` (no money is involved). At minimum, document that `Launched` holds capacity until it is resolved.

### [medium] `DaemonRuntime::unsubscribe_channel` and migration teardown unsubscribe the whole node, cutting off co-located daemons on the same (publisher, channel); `stop`/`shutdown` never tear down the ledger
- **Where:** `net/crates/net/sdk/src/compute.rs:1254-1278` (`unsubscribe_channel`), `compute.rs:601-617` and `:1851-1868` (`pre_cleanup` → `teardown_subscriptions`), `compute.rs:1059-1073` (`stop`), `compute.rs:660-698` (`shutdown`). Core: `src/adapter/net/mesh.rs:35911-35918`. `unsubscribe_channel` sends a node-level membership leave, with no per-daemon refcount.
- **Verdict:** PLAUSIBLE. The unverified link is that the publisher-side roster is keyed per subscriber node. The SDK side is traced: it keeps per-daemon ledgers but sends node-level subscribe and unsubscribe with no refcount across daemons.
- **Problem:** Subscriptions are recorded per daemon but enforced per node. When daemon A unsubscribes, or is migrated away and its `pre_cleanup` teardown runs, the node leaves the publisher's roster even though daemon B on the same node still has `(publisher, channel)` in its ledger. In the other direction, `stop()` and `shutdown()` drop hosts without sending any unsubscribe, so the node stays on publisher rosters for daemons that no longer exist until the session times out.
- **Failure scenario:** Daemons A and B on node N both subscribe to `(P, "prices")`. A migrates to node M. At cutover, N's `pre_cleanup` sends Unsubscribe(P, prices). P drops N from the roster and B stops receiving events, with no error anywhere.
- **Fix sketch:** Refcount `(publisher, channel)` across the runtime's live hosts. Send the wire unsubscribe only when the last ledger entry goes. Have `stop`/`shutdown` walk the ledger through the same refcounted path.

### [low] `MigrationHandle` retry path leaks the orchestrator record when a send fails, and every later `start_migration` returns `AlreadyMigrating`
- **Where:** `net/crates/net/sdk/src/compute.rs:2162-2164` (`reinitiate_attempt`: `send_migration_message(..).await?`, no abort). Compare `start_migration_with` at `compute.rs:1471-1478`, which aborts on send failure. Core: `orchestrator.rs:1248-1251` (`start_migration` refuses an existing record).
- **Verdict:** CONFIRMED
- **Problem:** After a `NotReady` retry re-creates the orchestrator record, a failed initial send (for example `peer_addr` returning `None` because the peer dropped) returns `Err` from `wait()` with the new record still registered. Nothing removes it.
- **Failure scenario:** The target is still starting (`NotReady`), and then the link to the source drops during the backoff. `wait()` returns `TargetUnavailable`. The operator calls `start_migration` again and gets `AlreadyMigrating` until restart. A plain `wait()` on another clone polls `Some(phase)` forever.
- **Fix sketch:** Mirror `start_migration_with`: call `orchestrator.abort_migration(origin, "retry send failed")` before propagating the error.

### [low] `TaskRegistry::forget` on an in-flight task orphans a running executor (it can no longer be cancelled) and allows a second run of the same id
- **Where:** `net/crates/net/sdk/src/a2a.rs:1409-1416` (`forget` removes any entry, terminal or not). Related: `a2a.rs:1473-1492` (`set_state` no-ops on a missing entry, so the hook never fires) and `a2a.rs:1236-1280` (`reserve` inserts a fresh entry).
- **Verdict:** CONFIRMED
- **Problem:** `forget` is documented as housekeeping "once the requester has the result", but it does not refuse non-terminal entries, unlike the journal's `forget`, which refuses anything but `Terminal` (`a2a_journal.rs:1857-1870`). Removing a `Running` entry drops the only handle to its `CancelToken`. The spawned task keeps running and its terminal `set_state` lands nowhere. On the free path, a later identical submit finds no entry and launches a second executor.
- **Failure scenario:** A host operator's cleanup loop calls `registry.forget(owner, id)` for tasks it has "seen". It catches one still running. `cancel_task` now returns `false` while the work keeps running, and the requester's retransmit starts a duplicate run.
- **Fix sketch:** Refuse (return `false`) unless `e.state.is_terminal()`, matching the journal's `forget` contract.

### [low] Game-anchor open-game state file: unsynchronized `append_state` vs `write_state` (rename) loses entries; concurrent `write_state` calls share one `.tmp` name
- **Where:** `net/crates/net/sdk/src/game_anchor.rs:581-582` (`open_game` → `append_state`), `game_anchor.rs:588-616` (`reclaim_idle` → `write_state`), `game_anchor.rs:618-658` (both write `path` with no lock; `write_state` always uses `<path>.tmp`).
- **Verdict:** CONFIRMED (the race window is real; the impact is limited to restart persistence)
- **Problem:** `write_state` takes its snapshot of `games` under a read lock, releases the lock, and then writes and renames. An `append_state` for a game created between the snapshot and the rename appends to the old inode, which the rename then replaces, so the line is lost. Two concurrent `write_state` calls (concurrent reclaims) write the same `.tmp` file at once and can publish an interleaved file.
- **Failure scenario:** At capacity, request X triggers `reclaim_idle` while request Y creates the open game `("https://a.example", "chess")`. Y's line is lost from the state file. After an anchor restart that game is forgotten, and reconnecting pages holding pre-restart invites are refused (`UNKNOWN_INVITE`). `state_write_errors` does not count this, because no write failed.
- **Fix sketch:** Serialize all state-file writes under one mutex, take the snapshot inside it, and use a unique temp name. Or always rewrite (no append) under that mutex.

### [high] Filtered `EventStream` / `TypedChannel.subscribe()` stalls forever behind a run of non-matching events
- **Where:** `sdk-ts/src/stream.ts:178-213` (cursor only advanced inside `if (response.events.length > 0)`); reached from `sdk-ts/src/channel.ts:203-214` (`TypedChannel.subscribe`/`subscribeRaw` always set a `_channel` filter) and `NetNode.subscribe({filter})`. Core contract: `src/consumer/merge.rs:937-951` (and 897-899).
- **Verdict:** CONFIRMED
- **Problem:** Filtering runs after retrieval (`consumer/filter.rs` header). When a poll fetches a window in which every event is filtered out, the core returns `events: []` together with an advanced `next_id` and `has_more: true`. It says so explicitly: "Return the cursor even when all events were filtered out, so the caller advances past the filtered region instead of re-fetching the same events forever". `EventStream` drops that `nextId` in the empty branch and re-polls from the old cursor, which is `undefined` (stream start) on the first poll.
- **Failure scenario:** On a Redis/JetStream bus, other producers write ≥ `limit × 3 / shards` events per shard (the filter over-fetch window, `merge.rs:567`) before the first `sensors/temp` event. `node.channel('sensors/temp').subscribe()` then re-fetches that same window forever, backs off to 100 ms, and never yields anything. There is no error and no CPU spike, so it looks like an idle channel. The vitest mock (`test/channel_tag.test.ts:34-43`) doesn't model filtering, so nothing catches this.
- **Fix sketch:** Always take `response.nextId` when it is non-null, even with zero events. Skip the idle backoff when `response.hasMore` is true.

### [high] `DaemonRuntime.registerFactory` hands the raw user factory to native, which invokes it with unbound methods and can't handle async factories (breaks migration-in and groups); same `this` loss in `MeshOsDaemonSdk.registerDaemon`
- **Where:** `sdk-ts/src/compute.ts` `registerFactory` (comment block about "the native side only records the kind"), `spawn` / `spawnFromSnapshot` (local path binds methods correctly); `bindings/node/src/compute.rs:462-525` (registers a factory closure with the core SDK that calls the JS factory via TSFN), `:267-335` (`DaemonBridgeTsfns::from_napi_value` pulls `process`/`snapshot`/`restore` off the object with `get_named_property`); napi-rs 3.14.2 `threadsafe_function.rs:948-949` (TSFN receiver is `napi_get_undefined`). Also `sdk-ts/src/meshos.ts` `registerDaemon` → `bindings/node/src/meshos.rs:478-522` (same extraction pattern).
- **Verdict:** CONFIRMED. Every link was read; the `this === undefined` outcome follows from the receiver being undefined plus strict-mode class methods.

The native layer calls the stored factory whenever a daemon is reconstructed outside `spawn()`: migration target (`expectMigration` / `registerMigrationTargetIdentity`) and `ReplicaGroup` / `ForkGroup` / `StandbyGroup` spawn and failover. It then calls each extracted method with `this = undefined`. The SDK's own `DaemonFactory = () => MeshDaemon | Promise<MeshDaemon>` type allows async factories, and the binding rejects those on this path (its own caveat at `compute.rs:501-508`). Separately, on the local `spawn()` path `requiredCapabilities` / `optionalCapabilities` are dropped (`compute.rs:615-618`). The `MeshDaemon` docs say these "drive the substrate's `MeshDaemon::required_capabilities`".
- **Failure scenario:** `groups.ts` module docs show `rt.registerFactory('counter', () => new CounterDaemon())`. If `CounterDaemon.process` touches `this.count`, it throws `TypeError` on every event in every group member and on every migrated-in daemon, while the same class works under `rt.spawn()`. An `async () => new Model(await load())` factory works for `spawn()` and fails every migration and group spawn. Tests only use `NoopDaemon`, which never touches `this` (`test/groups.test.ts:31-36`), so CI stays green.

### [medium] A throwing `onStreamData` handler is a fatal process exception; `meshStoreTransport` fans out to store and app handlers with no isolation
- **Where:** `sdk-ts/src/mesh.ts` `onStreamData` (calls `handler(...)` bare inside the native callback); `sdk-ts/src/store-transport.ts:119-127` (`for (const handler of [...handlers]) handler(frame)`); `bindings/node/src/lib.rs:2240-2249` (fire-and-forget `tsfn.call(..., NonBlocking)`); napi-rs 3.14.2 `threadsafe_function.rs:984-1000` (`handle_call_js_cb_status` → `napi_fatal_exception` on a pending JS exception).
- **Verdict:** CONFIRMED for the mechanism (any throw goes to `uncaughtException`, and by default the process exits). PLAUSIBLE for remote triggering (unverified link: whether `@net-mesh/browser` hostStore's `authorize` / `actions` / `inputs` callbacks are wrapped; the frame-decode path in `browser-ts/src/store/host.ts:613-650` is defensive).
- **Problem:** The SDK neither documents nor isolates this. One throwing handler also stops delivery to every later handler for that frame.
- **Failure scenario:** On a dedicated game host, peer-supplied data makes a user `authorize` or `action` callback throw. The whole host process dies, which is a remote DoS on every connected player.
- **Fix sketch:** Wrap the user handler in `onStreamData` (and each handler in the store-transport loop) in try/catch, and route errors to an optional `onError` or `queueMicrotask(() => { throw e })`. Document the behavior.

### [medium] Deck `status()` / `snapshots()` / audit records / `blastRadius()` parse u64 ids with plain `JSON.parse` and lose precision
- **Where:** `sdk-ts/src/deck.ts:261, 414, 621, 691, 816`; the source JSON is `serde_json::to_string` in `bindings/node/src/deck.rs:331, 686, 962, 1064, 1405`; the u64 fields include `MigrationSnapshot.daemon_origin` / `source_node` / `target_node` and `MeshOsSnapshot.runtime_epoch_id` (`src/adapter/net/behavior/meshos/snapshot.rs:105-140`).
- **Verdict:** CONFIRMED

The id is off by up to ~2^11, so the command targets a nonexistent or wrong daemon. Node-id comparisons against `mesh.nodeId()` (bigint) never match.

### [medium] CortEX `watch` / `snapshotAndWatch` / `RedexFile.tail` iterables cannot be cancelled while waiting, and leak the native iterator when `next()` rejects
- **Where:** `sdk-ts/src/cortex.ts:489-515` (`wrapWatchIter`), `:422-444` (`tail`), `:698-726`, `:905-927`; the same rejection-path gap exists in the deck stream wrappers (`sdk-ts/src/deck.ts:251-300, 557-630`). - **Verdict:** CONFIRMED

### [low] `meshStoreTransport` stream `close()` (and `transport.close()`) never closes the native stream

# Node napi binding audit — `net/crates/net/bindings/node/`

Static, read-only. Paths are repo-relative to `net/crates/net/`.

Overall: the binding is heavily hardened. Most TSFN sites use `NonBlocking` plus a swallowed send on a dropped receiver, are not callee-handled (so a JS throw becomes `Err` rather than a fatal crash), and put a single deadline over both the dispatch and the promise stages (org, streaming nRPC, publish, a2a, blob-async). Consent, pins, delegation, the capability gateway and org are thin forwards to `net_sdk` / `net_mcp`, and I found no fail-open drift from SDK semantics in them. The real defects are in the places that missed those shared patterns.

---

### [medium] Unary `MeshRpc.serve` handler timeout does not bound the promise, so a never-settling async handler holds the call forever
- **Where:** `bindings/node/src/mesh_rpc.rs:415` (timeout wraps only `rx`, stage 1); `:452` (`promise.await`, stage 2, unbounded). The documented contract is at `:2025-2031`. Compare the fixed siblings: `:1676/:1696`, `:1774/:1794` and `:1886/:1906` (streaming), and `src/org.rs:646-705`, whose comment names this exact bug: "an unbounded stage-2 `promise.await` previously made the timeout a no-op".
- **Verdict:** CONFIRMED
- **Problem:** `handlerTimeoutMs` (default 60 s) only covers the TSFN dispatch until JS *returns* a Promise. An `async` handler returns its Promise immediately, so in practice the cap never applies. The core does not save it either: `cortex/rpc.rs:2195` awaits `handler.call(ctx)` with no deadline, and `NodeRpcHandler` ignores `ctx.cancellation`.
- **Failure scenario:** `rpc.serve("svc", async () => new Promise(() => {}))`, or `TypedMeshRpc.serve`, which always wraps the handler in an `async` function (`mesh_rpc.ts:589`). Every request leaves a spawned task, a `handler_in_flight` count and the request buffers held forever. The caller sees only its own deadline, never the documented `Internal "JS handler did not respond within N ms"`. Repeated calls leak without bound.
- **Fix sketch:** Compute `deadline = Instant::now() + timeout` once and wrap both `rx` and `promise` in `timeout_at(deadline, …)`, as `dispatch_to_js` in org.rs does. `Some(0)` must then map to a "no deadline" branch, because `Instant + u64::MAX/1000 s` would overflow.

### [medium] `onStreamData` subscription: an unbounded TSFN queue fed by remote peers, a ref'd event loop, and no `Drop`
- **Where:** `bindings/node/src/lib.rs:2232-2276` (`on_stream_data`), `:1141-1172` (`StreamDataSubscription`, which has no `impl Drop`). napi 3.x defaults are `Weak=false` and `MaxQueueSize=0`, meaning referenced and unbounded (`napi-3.14.x/src/threadsafe_function.rs:194-195`).
- **Verdict:** CONFIRMED
- **Problem:**
  1. The sink runs on the mesh receive path and calls `tsfn.call(…, NonBlocking)` into an unbounded queue, copying each payload (`to_vec()`). Nothing bounds or drops events. The core deliberately offers `open_stream_inbox` with a capacity and drop counter for callers that can't run on the receive path (`src/adapter/net/mesh.rs:34372-34381`), and Python uses it. Node does not.
  2. The TSFN is ref'd, so a forgotten subscription keeps the process alive.
  3. With no `Drop`, a subscription that is GC'd without `close()` leaves the registration in `node.stream_inbound` forever. The stream id then stays claimed: a later `onStreamData` for it throws "already has a subscription". The TSFN, and with it the event loop ref, live until `shutdown()`.
- **Failure scenario:** An authenticated peer floods a subscribed stream while the JS thread is busy, and RSS grows without bound because the receive loop never applies backpressure. Separately, a short-lived subscription object goes out of scope without `close()`: the process never exits, and the stream id can't be re-subscribed.
- **Fix sketch:** Build the TSFN with `.max_queue_size::<N>()` and count `QueueFull` drops, or move to `open_stream_inbox` with a JS pump. Add `impl Drop for StreamDataSubscription` that calls `close()`.

### [low] `MeshRpc.setObserver` drop policy is defeated: a bounded channel drains into an unbounded TSFN
- **Where:** `bindings/node/src/mesh_rpc.rs:2410-2440`. The bounded `ObserverChannel` is in `src/adapter/net/cortex/rpc_observer.rs:160`.
- **Verdict:** CONFIRMED
- **Problem:** The docstring says events are "**dropped**, not buffered" when the JS loop is wedged and the queue fills. The drain worker forwards each event straight into a default (unbounded) TSFN with `NonBlocking`, which never returns `QueueFull`. The bounded channel therefore never fills, `observer_dropped_total` stays at 0, and events pile up in napi's queue. The ref'd TSFN also keeps the process alive until `setObserver(undefined)`.
- **Failure scenario:** High outbound RPC rate while the event loop is blocked leads to unbounded memory growth, and the metrics report no drops.
- **Fix sketch:** Give the observer TSFN a `max_queue_size`, or have the drain worker treat `QueueFull` as a counted drop.

### [low] Several u64 BigInt arguments bypass `common::bigint_u64`, so negative or oversized values are silently reinterpreted
- **Where:**
  - `bindings/node/src/blob.rs:1349-1350` (`fetchRange` start/end ignore both `signed` and `lossless`)
  - `src/blob.rs:291` (`BlobRef` size ignores `lossless`)
  - `src/lib.rs:2048` (`shardForStream`)
  - `src/capability_aggregation.rs:138` (RTT `nodeId`)
- **Verdict:** CONFIRMED
- **Problem:** napi's `get_u64()` returns the magnitude's low word. `-5n` reads as `5`, and `2n**64n + 3n` reads as `3`. `common.rs:15-42` exists precisely to reject these, and every other u64 site uses it.
- **Failure scenario:** `adapter.fetchRange(ref, -1n, 10n)` returns bytes `[1,10)` with no error, and since partial fetches are not hash-verified this is silent data. A wrong `nodeId` in `rttEntries` attaches the RTT to another node and changes the capacity ranking. `new BlobRef(uri, h, 2n**64n)` records size 0.
- **Fix sketch:** Route all four through `crate::common::bigint_u64`.

### [low] `CallOptions.cancelToken`: a malformed token is silently discarded, so the call becomes uncancellable
- **Where:** `bindings/node/src/mesh_rpc.rs:284-290` (`.transpose().ok().flatten()`)
- **Verdict:** CONFIRMED
- **Problem:** A negative or >u64 `cancelToken` fails `bigint_u64`, and the error is dropped. The call then runs with no cancel token, and a later `cancelCall(token)` is a no-op.
- **Failure scenario:** A caller wires an AbortSignal using a corrupted token value. The abort does nothing and the call runs to its deadline (or forever, with no deadline).
- **Fix sketch:** Make `into_inner` fallible and reject the call with an `nrpc:` error.

### [low] `handlerTimeoutMs: 0` means "disable" on most serve verbs but "time out immediately" on `publishTools` and blob adapters
- **Where:** `bindings/node/src/publish.rs:292-294` (`build_tool_invoker`) and `src/blob.rs:811-813` / `:1082-1084` give 0 ms, so every call fails. Compare `src/mesh_rpc.rs:2041`, `src/org.rs:561` and `src/a2a.rs:207`, where 0 disables the cap.
- **Verdict:** CONFIRMED
- **Problem:** The same knob has inverted semantics across sibling verbs. On `publishTools` (and the paid path, which shares `build_tool_invoker`), 0 turns every tool invocation into a `Transport` error ("did not return a Promise within 0 ms").
- **Fix sketch:** Map `Some(0)` to "unbounded" (or reject it) consistently, and document it.

### [high] Filtered subscriptions livelock: the cursor is never advanced when a poll's whole window is filtered out
- **Where:** `sdk-py/src/net_sdk/stream.py:97-110` (`__iter__`) and `:130-143` (`__aiter__`). The cursor is updated only inside `if len(response) > 0`. The SDK always filters in `sdk-py/src/net_sdk/channel.py:236-238` and `:271-273` (`TypedChannel.subscribe` / `subscribe_raw`), and also when a caller passes `NetNode.subscribe(filter=...)`. The same bug exists in the TS SDK: `sdk-ts/src/stream.ts:65-67`.
- **Verdict:** CONFIRMED
- **Problem:** On the filter path the core merger advances past every fetched event. When the filter removes all of them, it returns `events=[]`, `next_id=<advanced cursor>`, `has_more=true` (`src/consumer/merge.rs:903-950`, comment: "Return the cursor even when all events were filtered out, so the caller advances past the filtered region instead of re-fetching the same events forever"). The SDK drops that `next_id` and re-polls from its old cursor, which is `None` (the start of the log) for a fresh subscription.
- **Failure scenario:** A Redis- or JetStream-backed `NetNode` with `shards=4` and the default `limit=100` fetches up to `ceil(100/4)*3 = 75` events per shard. Suppose ≥75 events from channel B (or any other untagged emits) sit at the head of every shard, followed by events on channel A. `node.channel("a").subscribe()` then re-fetches the same 75-per-shard window of B events forever, backing off to 100 ms. It never yields an A event, including ones published later. This is a silent hang with no error. It is the normal case for a quiet channel on a shared bus.
- **Fix sketch:** Always take `response.next_id` when it is not None, even when `len(response) == 0`. Skip the idle backoff when `response.has_more`. Apply the same fix to `sdk-ts/src/stream.ts`.

### [medium] The MeshOS handle's `_borrow_lock` is held across the blocking `next_control`, which can deadlock, and is taken on the event-loop thread
- **Where:** `sdk-py/src/net_sdk/meshos.py:344-351` (`next_control` holds a `threading.Lock` for the whole blocking call), `:389-397` and `:417-422` (`anext_control` / `__anext__` acquire the same lock on the loop thread), `:444-451` (`graceful_shutdown` holds it for the grace period). Native side: `bindings/python/src/meshos.rs:767-797` blocks via `py.detach(block_on(...))` with no timeout when `timeout_ms=None`. `:860-882` blocks for `grace` (`DEFAULT_GRACEFUL_SHUTDOWN` = 5 s, `src/adapter/net/behavior/meshos/sdk.rs:82`).
- **Verdict:** CONFIRMED
- **Problem:** The lock was added to avoid PyO3 "Already borrowed" errors, but it is a blocking `threading.Lock`. It is held across calls that block indefinitely and is acquired from coroutines.
- **Failure scenario:**
  1. Thread A runs `handle.next_control()` (no timeout) and waits for a control event. Thread B calls `handle.graceful_shutdown()`, which is the call that would route the `Shutdown` event that wakes A. B blocks on the lock instead, so the shutdown never happens. This is a deadlock until some unrelated control event arrives. Without the wrapper's lock, B would get an immediate borrow error rather than a hang.
  2. The class docstring recommends `async for ev in handle` together with `await loop.run_in_executor(None, handle.graceful_shutdown)`. The executor thread holds the lock for up to the 5 s grace while `__anext__` calls `with self._borrow_lock` on the loop thread, so the whole event loop is frozen for the grace period.
  3. Separately, `anext_control(timeout_ms=None)` returns `None` after 100 ms, while its docstring says "same semantics as the sync variant" (which blocks until an event arrives).
- **Fix sketch:** Don't hold the lock across the blocking native call. Use `next_control` with short timeouts in a loop, releasing the lock between iterations, or use the native `AsyncMeshOsDaemonHandle`. In async paths use a non-blocking `lock.acquire(blocking=False)` plus a sleep, or an `asyncio.Lock` together with `to_thread`.

### [medium] `EventStream.__aiter__` runs a blocking, network-bound poll on the event loop
- **Where:** `sdk-py/src/net_sdk/stream.py:130` (`response = self._poll()` inside `async def __aiter__`), which calls `Net.poll` at `bindings/python/src/lib.rs:764-805`. That method runs `self.runtime.block_on(bus.poll(request))` with no GIL release.

### [high] A second `publish_tools` on the same node fails and wipes the first publication's announcement
- **Where:** `src/publish.rs:166-186` (`mesh_publish_tools_configured` builds `mesh_over(node)` plus `ServerPublisher::new(mesh)` on every call). Callers: `src/lib.rs:1975` (`NetMesh.publish_tools`) and `src/payment_provider.rs:682` (paid `publish_tools`). Its docs say "all publications made through it (and its clones) merge into the node's single announcement". The binding builds a fresh publisher for every call, so two publications on one node never share that state.
- **Failure scenario:**

  2. `h2 = mesh.publish_tools([...B])` (or the paid path on the same node) starts. Its `sync_mesh` announces only B. Announcements replace the whole node set (`session.rs:305`), so A's tags are gone.

  5. Result: the call raises `publish_tools failed`, and the node now announces nothing. A's tools are still served but can no longer be discovered.

- **Fix sketch:** Keep one `ServerPublisher` per node and reuse it. Either store a lazily-built `ServerPublisher` (over one long-lived `Arc<Mesh>`) on `NetMesh`, or keep a node-keyed registry, and route both the free and paid paths through it.

### [medium] Sync stream `close()` is a no-op while another thread is in `__next__`, and the call comes back to life (no CANCEL)
- **Where:**
  - `src/mesh_rpc.rs:1047-1116`: `PyRpcStream.__next__` / `close` / `grant`.
  - `:1262-1460`: `PyDuplexCall.send` / `finish_sending` / `__next__` / `close`.
  - `:1170-1245`: `PyClientStreamCall.send` / `close`.
  - `PyDuplexSink` and `PyDuplexStream` close at `:1543` and `:1615`.
- **Verdict:** CONFIRMED.
- **Problem:** Each blocking method takes the inner call out of the `parking_lot::Mutex<Option<_>>`, awaits with the GIL released, and then puts it back. `close()` only does `inner.lock().take()`. If it runs while another thread holds the taken value, it finds `None` and does nothing. When that thread finishes it writes the call back, so the call is live again. `__next__` and `finish_sending` do not select on `close_notify` at all.
  - The async siblings were already fixed for this exact defect. The comment at `src/mesh_rpc.rs:3286-3290` says "the take/put pattern that races with `close()` (a parking_lot put-back resurrects an inner the close had just cleared)". The sync classes were not fixed.
- **Failure scenarios:**
  - **Reader cannot be stopped.** A reader thread runs `for chunk in stream:` on a server stream that is idle. The main thread calls `stream.close()`, or leaves a `with` block. No CANCEL is sent, and the reader stays blocked until the server happens to send. When the server sends, the stream is put back and iteration continues as if `close()` never happened. The server-side handler keeps running.
  - **Lost credit grant.** `PyRpcStream.grant(n)` from another thread, while the consumer is parked in `__next__`, is silently dropped because `inner` is `None`. On a flow-controlled stream whose window is exhausted, the server never gets the credit, so this is a permanent stall.
- **Fix sketch:** Mirror the async design. Add a `closed: AtomicBool` that is checked when a value is put back (drop the call instead of restoring it). Have `__next__` and `finish_sending` `select!` on `close_notify`. Hold `grant` and flow-control handles outside the taken value, or let `grant` reach the stream while it is taken.

### [medium] Sync `NetMesh` and `Net` methods hold the GIL across network or mesh waits
- **Where:**
  - `src/lib.rs`:
    - `NetMesh.push_to` (2158), `poll_shard` (2183), `poll` (2219)
    - `subscribe_channel` (2571-2583, waits for the membership ack), `unsubscribe_channel` (2593)
    - `publish` (2655, reliable publish waits for per-subscriber acks)
    - `shutdown` (3425, `MeshNode::shutdown` joins every background task with a 2 s timeout, then aborts and waits up to 2 s again; see `src/adapter/net/mesh.rs:52496-52590`)
    - `Net.poll` (803), `flush` (874), `shutdown` (883), each a `block_on` on the bus adapter (Redis or JetStream I/O)
  - `src/payment_provider.rs:576`: `pricing_terms` → `engine.check_settlement_routes`.
- **Verdict:** CONFIRMED that the GIL is held: these sites call `self.runtime.block_on` directly, unlike the roughly 150 `py.detach` sites in the crate. The comment at `lib.rs:2676` documents this as a bug class that was fixed for `announce_capabilities`. PLAUSIBLE that this can turn into a deadlock rather than a stall. The unverified link is that a task the blocked future depends on sits on a tokio worker that is itself parked in `Python::attach`. Inline-attach callbacks exist (`placement.rs:93`, `compute.rs:1000`, `meshos.rs:485`, `subnet.rs:76`), and tokio's LIFO slot cannot be stolen.
- **Failure scenario:** A reliable `mesh.publish(...)` to a slow subscriber, or `mesh.shutdown()` with N background tasks (up to about 4 s each), freezes every other Python thread for the whole wait. - **Fix sketch:** Wrap each of these in `py.detach(|| self.runtime.block_on(...))`, as the neighbouring methods do. For `Net.flush` and `shutdown`, take a cloned handle out of the `RwLock` before detaching.

### [medium] `AsyncNetMesh` does not keep the source `NetMesh`'s runtime alive, and that runtime owns the node's socket reactor
- **Where:** `src/lib.rs:3669-3693` (`AsyncNetMesh { node, recv_cursor }`, with no runtime field). Compare `PyAsyncMeshRpc` at `src/mesh_rpc.rs:2845-2853`, which does hold `runtime: Arc<GuardedRuntime>`.

### [high] A failed `RegisterDaemonWithCallbacks` deletes the cgo.Handle twice, and the second delete panics the caller (process crash)
- **Where:** `go/meshos.go:757-767` (Go `cgoHandle.Delete()` on the error path, with the comment "Rust never took ownership"); `net/crates/net/bindings/go/meshos-ffi/src/lib.rs:991-1023` (`CDaemonBridge` boxed **before** the SDK-alive check and before `register_daemon`); `CDaemonBridge::drop` at `meshos-ffi/src/lib.rs:511-525` → `goMeshOsDestroyUserCtx` at `go/meshos.go:828-840` (which already runs `Delete`).
- **Verdict:** CONFIRMED. I traced the `already_shutdown` path myself: the `daemon` box is dropped on `return NET_MESHOS_ERR_ALREADY_SHUTDOWN`. That runs `destroy` → Go `Delete`, and Go then runs `Delete` again. The `register_daemon` Err path drops the bridge through the registry in the same way.
- **Problem:** On every post-construction failure, Rust has already destroyed the user context. The Go wrapper assumes it has not and deletes the handle again. `cgo.Handle.Delete` on an invalid handle panics ("misuse of an invalid Handle"). This happens in plain Go code with no recover, in the caller's goroutine.
- **Failure scenario:** Either of these crashes the process:
  - register two callback daemons with the same seed (registry "already registered");
  - call `RegisterDaemonWithCallbacks` after `sdk.Shutdown()`.

  A C consumer following `net_meshos.h` (which says nothing about ownership on failure) double-frees its `user_ctx` in the same way.
- **Fix sketch:** In Rust, construct the bridge only after the alive check. On the `register_daemon` error, disarm the destructor (`destroy = None`) before the drop, and document "on failure the caller still owns user_ctx" in the header. Alternatively, remove the Go-side Delete and handle the pre-bridge validation returns separately.

### [high] `MeshRpc.Close` / `OrgClient.Close` deadlock with the ctx-cancel watcher, so cancellation never reaches Rust
- **Where:**
  - rpc: `go/mesh_rpc.go:623-637` (`withHandle` holds the RLock across the blocking cgo call), `:654-665` (`Close` takes `Lock`), `:941-954` (the watcher calls `withHandle` again before `net_rpc_cancel_call`); used by `Call` at `:770` and `CallService` at `:808`.
  - org: the same shape at `go/org.go:608-632` and `:773-784` (`CallBytes` `:646`, `CallExportedBytes` `:684`).
  - Rust: `net_rpc_call` and `net_org_call` `block_on` until done or until a cancel token is fired.
- **Verdict:** CONFIRMED. I verified the rpc lock sequence. Go's `sync.RWMutex` refuses new `RLock`s once a writer is queued.
- **Problem:** A call parks in C while holding the RLock. `Close()` queues for the write lock. When the ctx is cancelled, the watcher blocks on `RLock`, so `net_*_cancel_call` never runs.
- **Failure scenario:** The usual shutdown `cancel(); client.Close()` with a cancel-only ctx (no deadline, so the Rust default applies: none for rpc, 300 s for org) against a silent peer. The call goroutine, the watcher, and `Close` all block, and so does every other method on that `MeshRpc`/`OrgClient`. For rpc this is permanent when the server never answers; even with a deadline, `Close` blocks for the call's whole remaining deadline, not "briefly" as documented.
- **Fix sketch:** Make cancel delivery independent of the handle lock. Either keep an in-flight token set that `Close` fires *before* `Lock()`, or have the watcher use the `h` captured under the caller's RLock and run `stopWatcher` inside the `withHandle` closure.

### [high] ctx cancel and `Close()` never reach Rust for streaming RPCs; a parked `Recv`/`Send`/`Finish` stays blocked
- **Where:**
  - Go constructors use the non-cancellable exports: `go/mesh_rpc.go:1157` (`net_rpc_call_streaming`), `:1223` (`CallServiceStreaming` with `cancel_token=0`), `:1621` (`net_rpc_call_client_stream`), `:1795` (`net_rpc_call_duplex`).

  - Rust: `rpc-ffi/src/lib.rs:1538ff` (`net_rpc_stream_next` takes the stream out of its mutex and then `block_on`, so `net_rpc_stream_close` at `:1639` finds `None`); `:2169ff` (`net_rpc_duplex_next` holds the mutex across `block_on`).
- **Verdict:** CONFIRMED for the Go→C→Rust chain. An unbounded hang additionally requires the substrate not to retire pending streams when the peer is lost; that link is unverified. Bounded hangs (up to the server's handler timeout) are confirmed.
- **Problem:** The `_cancellable` constructors exist (`net_rpc_call_streaming_cancellable`, `..._client_stream_cancellable`, `..._duplex_cancellable`, and a non-zero token for `call_service_streaming`), but the Go wrapper never uses them. A close cannot wake a parked `next`. This contradicts the end-to-end cancel promise in `go/mesh_rpc_typed.go:396-401` and `:762`.
- **Failure scenario:** `CallStreaming(ctx, …)` against a slow or partitioned server, followed by `cancel()` or `Close()`. `Close` returns, but the `Recv` goroutine stays blocked in C, holding an OS thread and the call slot, and no CANCEL frame is sent. ### [high] Group constructors use `rt.handle` without `rt.mu`, so `Close` or the finalizer frees the compute runtime mid-spawn (use-after-free)
- **Where:** `go/groups.go:325` (`NewReplicaGroup`), `:493` (`NewForkGroup`), `:649` (`NewStandbyGroup`); `go/compute.go:320-341` (`DaemonRuntime.Close` under `Lock`, also the finalizer); `compute-ffi/src/lib.rs:342-351` (`net_compute_runtime_free` = bare `Box::from_raw`, no HandleGuard); `:2472` (spawn dereferences `rt.inner`).
- **Verdict:** CONFIRMED. I verified that groups.go passes `rt.handle` with no lock and no `KeepAlive`, while every other `DaemonRuntime` method holds `rt.mu.RLock()`.
- **Problem:** A native group spawn runs factories, which can take a long time. `Close` does not wait for it and frees the runtime box. GC can also finalize `rt` mid-call if it is otherwise unreachable.
- **Failure scenario:** Goroutine A calls `NewReplicaGroup(rt, …)` while goroutine B calls `rt.Close()`, or `NewReplicaGroup(newRuntime(), …)` runs with no other reference. # Browser SDK (`browser-ts/`) + wasm leaf (`leaf/`) audit

Scope: `@net-mesh/browser` TS sources and the `net-leaf` wasm crate it rides. Static read only; nothing built.

### [high] A `LeafStream` with no consumer buffers every inbound frame forever, and the store, netcode and world layers all open streams they never read
- **Where:** `net/crates/net/browser-ts/src/stream.ts:118-121, 188, 260-266` (the `pending` array). Producers of unread streams: `browser-ts/src/store/host.ts:465-481` (one reply stream per peer, cached in `replies`), `browser-ts/src/store/join.ts:268-289` (`upstream`), `browser-ts/src/netcode/client.ts:203`, `browser-ts/src/netcode/host.ts:206`, `browser-ts/src/world/link.ts:183`. Rust filter: `leaf/src/wasm.rs:4325-4349` (`LeafStream::on_message`).
- **Verdict:** CONFIRMED. The one assumption is the documented property that both ends derive the same stream id from the label (`host.ts:87-94`). `arrivesOn` and the whole store design depend on that property.
- **Problem:** The `LeafStream` constructor always registers `inner.on_message(...)`. The wasm side forwards every `stream_data` event whose `peer_node` and `stream_id` match the handle. `receive()` pushes the payload into the unbounded `pending` array whenever `queues.size === 0 && listeners.size === 0`. The store, netcode and region-link layers use these streams only to `send()`. They read inbound traffic through `transport.onEvent(...)` and never iterate the stream or attach `onMessage`. So every frame the peer sends on that label is also appended to `pending` and never drained.
- **Failure scenario:** A lobby host serves 4 players. Each joiner's `upstream` stream receives every `delta`/`snap` the host sends. Each host reply stream receives every `alive`/`act`/`in` the player sends. Netcode is worse: the client's lossy stream receives a full snapshot every tick (20–60 Hz) and the host's per-player stream receives every input frame. All of it accumulates for the life of the store or game, which is hundreds of KB/s at netcode rates, until the tab runs out of memory. Host reply streams are also never closed when a peer leaves, only at `close()`, so departed players' streams keep their buffers. This contradicts `async-queue.ts:5-10` ("a page that stops consuming stops paying"). A stream whose last consumer left also falls back to buffering.
- **Fix sketch:** Do not buffer when no consumer has ever attached. Either make buffering opt-in (only after `onMessage`/iterator), or cap `pending` with a dropped-frame counter. Alternatively, give `StoreTransport.openStream` a send-only mode that skips `on_message` registration.

### [medium] Proxied org calls on a follower have no follower-side deadline: a frozen leader hangs them forever, and the documented `OrgIndeterminateError` cannot occur
- **Where:** `leaf/src/leader_session.rs:627-632` (the deadline is armed only for `LeaderRequest::Call`), `leaf/src/leader_session.rs:4106-4129` (`call_org`), `leader_session.rs:3648-3707` (`ProxyOrgCall::pull`/`poll`/`send`/`finish_sending`, which go through `Lifecycle::request` with no timer), `leader_session.rs:4344-4377` (`OrgCall` carries `timeout_ms`, but only the leader reads it). Contract: `browser-ts/src/leader/session.ts:487-497` and `browser-ts/src/org.ts:12-16`.
- **Verdict:** CONFIRMED.
- **Problem:** DESIGN.md's L4 repair arms a follower-side timer (`arm_deadline`) for unary `call` only, so a leader that is frozen while holding its Web Lock produces `rpc-indeterminate`. `LeaderRequest::OrgCall`, `OrgNext`, `OrgSend` and `OrgFinishSending` take the same `Lifecycle::request` path, but the `match` arms no deadline for them. The mapping of `Indeterminate` to a terminal at `leader_session.rs:3575` has no producer on the org path.
- **Failure scenario:** The leader tab is frozen (DESIGN.md measured that a frozen tab keeps its lock). A follower calls `session.callOrg(svc, bytes, { deadlineMs: 5000 })`. The promise never settles until the leader is resumed or closed, and `for await` on a `callOrgStreaming` stream parks indefinitely. The page never gets the documented `OrgIndeterminateError` / `OrgTimeoutError`. `openStream`, `publish` and `subscribe` on a follower have the same unbounded wait, but those are not documented as bounded.
- **Fix sketch:** Arm `arm_deadline` for `OrgCall` from its `timeout_ms`/`deadline_ns`, and give `OrgNext` long-pulls the call's absolute deadline. Map expiry to `Indeterminate`, as `Call` does.

### [medium] One authenticated peer can take all 256 store handles and lock every other player out; lobby capacity does not stop it
- **Where:** `browser-ts/src/store/owner.ts:1484-1521` (join checks only the global `MAX_HANDLES = 256`, `owner.ts:75`, with no per-peer cap). `browser-ts/src/lobby.ts:365-374` skips the capacity check for any peer already in `peersNow()`.
- **Verdict:** CONFIRMED.
- **Problem:** Every `join` that passes `authorize` installs a new handle and emits a full manifest and snapshot. A peer may hold any number of handles. The lobby's capacity rule counts distinct peers and explicitly exempts a peer that already has a handle (`!peersNow().includes(peer)`), so an admitted player's repeat joins bypass capacity. Repeat joins are always authorized under the default `authorize: () => true`.
- **Failure scenario:** A player in an 8-seat lobby sends 255 `join` frames and keeps them alive with `alive` every <60 s (`HANDLE_LEASE_MS`). Every other joiner, including legitimate players filling free seats, is refused with `capacity`. Each bogus join also costs the host a full projection and chunked snapshot, and every later commit fans a delta out to all 256 handles. The host's only remedy is a manual `kick`.
- **Fix sketch:** Cap handles per authenticated peer in `StoreOwner.join` (a small constant, or replace the peer's oldest handle). Count the lobby's capacity check on the same basis.

### [medium] `joinStore().reconnect()` drops the old upstream stream without closing it, and clears an in-flight open
- **Where:** `browser-ts/src/store/join.ts:782-803`
- **Verdict:** CONFIRMED for the leak. PLAUSIBLE that the orphan keeps buffering on the new session: the wasm filter (`wasm.rs:4328-4333`) matches on `peer_node` and `stream_id` text only, and I did not verify that a replaced session keeps the same derived id.
- **Problem:** `reconnect` sets `upstream = null; opening = null;` with no `upstream.close()`. The abandoned `LeafStream` stays in `BrowserNode.streams` and keeps its wasm listener registration. Every other path in this file closes a stream before dropping it (`send` at `join.ts:338-347`, `close` at `:836`). Nulling `opening` while an open is in flight lets that older open resolve later and set `upstream` over the new one, which orphans one of the two.
- **Failure scenario:** A page calls `world.reconnect()` on every `session_replaced`/network blip. Each call leaks one stream handle and its wasm listener. Because of the first finding, each leaked stream may also keep buffering every host frame that still matches its peer/id filter.
- **Fix sketch:** `const old = upstream; upstream = null; try { old?.close() } catch {}`. Leave a pending `opening` alone, or reject it, rather than nulling it.

### [medium] Two tabs using the recommended `connect()` + `rememberedIdentity()` run two nodes with one identity at the same time
- **Where:** `browser-ts/src/identity.ts:1-23, 65-87`; `browser-ts/README.md:579-583` (recommends the pattern and says two tabs are "the same player"); `browser-ts/src/node.ts:1212-1228` (`connect()` takes no Web Lock). Compare `leaf/src/leader_session.rs:144-160`, which refuses to run without Web Locks precisely so that two tabs cannot "evict each other under the identity-rebind rules".
- **Verdict:** PLAUSIBLE. Unverified link: the anchor-side rebind/eviction behaviour, taken from the leaf's own comment and not traced through the anchor.
- **Problem:** `openSession()` enforces one node per origin. The game path the README recommends (`connect()` with the secrets from `localStorage`) has no such guard. A second tab opened on the same site presents the same entity and Noise keys from a second session.
- **Failure scenario:** A player opens the game in two tabs. Both connect as the same node id. By the leaf's own description they evict each other at the anchor, so stores and lobbies in both tabs flap. The README only says "a player can't join itself", which does not warn about this.
- **Fix sketch:** Take a per-identity Web Lock in `connect()` when `entitySecretHex` is supplied, refusing or waiting typed. Alternatively, document the hazard and steer multi-tab games to `openSession`.

### [low] Stores over a `MeshSession` break permanently after a leader handoff: closed streams are never reopened
- **Where:** `browser-ts/src/leader/session.ts:179-203, 913-917` (`endStreams` closes every handed-out stream when the generation moves); `browser-ts/src/stream.ts:211-212` (`send` on a closed stream throws `SessionError('the stream is closed')`); `browser-ts/src/store/errors.ts:97-100` (`isStaleStream` matches only `'stale stream handle'`); `store/host.ts:518`, `store/join.ts:330`.

- **Fix sketch:** Treat the local-closed / `not-leader` refusal as reopenable in `isStaleStream`, or have the store drop cached streams on `leader_changed`. Otherwise refuse a `MeshSession` transport loudly.

### [low] `joinStore({ key })` is documented as read by the host's policy, but it never reaches `authorize`
- **Where:** `browser-ts/src/store/join.ts:99-100` ("The opaque key the host's policy reads"), `browser-ts/src/store/replica.ts:110`; `browser-ts/src/store/types.ts:187-204` (`AccessRequest` has no `key`); `browser-ts/src/store/owner.ts:1490, 1576-1583` (`permitsRead` builds `{type, peer, audience}` and drops `message.key`).

### [low] ICE-failure classification: "gathering completed with no reflexive candidate" is counted as unanswered, so a host without NAT can be classed `udp-blocked`
- **Where:** `browser-ts/src/udp-probe.ts:233-238, 265-267` (`gatheringDone` settles `unanswered` without consulting `gathered`); the Rust probe applies the same rule (`leaf/src/wasm.rs:4101-4108`).

# Cross-SDK parity audit (slice: semantic drift across Rust / TS+Node / Python+PyO3 / Go / C)

Static read only; nothing built or run. Paths are relative to `net/crates/net/` unless they start with `go/` or `.github/`.

Headline: the security-critical decisions are well centralised. Consent, pins, org admission, delegation verification, blob hash verification and revocation-store loading all run once in Rust (`net_sdk` / core), and every binding forwards to that code. The drift sits in the **binding glue**: how each language turns "field omitted / empty / zero" into a core value. In one place (Go channel token roots) that makes Go fail **open** where every other language fails closed.

---

### [medium] Go registers an OPEN channel when TokenRoots is an empty slice; every other SDK registers a locked one
- **Where:** `go/mesh.go:408` (`TokenRoots []string \`json:"token_roots,omitempty"\``) → `src/ffi/mesh.rs:2499-2512`. Compare Node `bindings/node/src/lib.rs:1467-1478`, Python `bindings/python/src/lib.rs:2512-2523`, core `src/adapter/net/channel/config.rs:321-324,338-340`.
- **Verdict:** CONFIRMED
- **Problem:** Core `with_token_roots(roots)` always sets `require_token = true`, even when `roots` is empty, so the channel refuses everyone. Node, Python, raw C JSON (`"token_roots":[]`) and Rust all reach that call with an empty list. Go's `encoding/json` drops an empty slice under `omitempty`, so the FFI sees `token_roots: None`, never calls `with_token_roots`, and `require_token` stays at its default of `false`.
- **Failure scenario:** An operator loads the trusted roots from config, and the list comes back empty (missing file section, filter matched nothing). The code is `ChannelConfig{Name: "ops/cmd", TokenRoots: roots}`. In Node, Python, C and Rust the channel is token-gated with no roots, so nobody can subscribe. In Go the same program registers an unauthenticated, Global channel, and any peer can subscribe to `ops/cmd`.
- **Fix sketch:** Either drop `omitempty` from `TokenRoots`, or make the field `*[]string`, so that an empty non-nil slice is sent as `[]`. Add a Go test asserting that `TokenRoots: []string{}` rejects subscribers, mirroring the other bindings.

### [medium] A zero heartbeat or session timeout behaves three different ways: rejected (C), busy-loop (Node / Python / Rust SDK), silently replaced (Go)
- **Where:** FFI guard at `src/ffi/mesh.rs:635-653`; pass-through with no check at Node `bindings/node/src/lib.rs:1758-1763`, Python `bindings/python/src/lib.rs:1549`, Rust SDK `sdk/src/mesh.rs:280-289,518-519`; Go `go/mesh.go:236-237` (`omitempty`); the heartbeat loop at `src/adapter/net/mesh.rs:33161,33211` (`tokio::time::sleep(interval)`).
- **Verdict:** CONFIRMED. The "busy-loops" consequence is what the FFI's own guard comment says; the loop is a `select!` on `sleep(interval)`.
- **Problem:** The FFI comment reads "A zero heartbeat interval busy-loops the heartbeat task (saturating a CPU); a zero session timeout makes every session expire instantly", and it rejects 0. Only the C path has that guard. `MeshNodeConfig` has no validation of its own; only `NetAdapterConfig::validate` has one, at `src/adapter/net/config.rs:280-294`. Go never reaches the guard because `omitempty` drops the 0, so Go quietly uses 5 s / 30 s.
- **Failure scenario:** `new NetMesh({ heartbeatIntervalMs: 0 })`, `NetMesh(heartbeat_interval_ms=0)` or `MeshBuilder::heartbeat_ms(0)`: one core pegs on heartbeat sends, and with `session_timeout_ms: 0` every session is torn down immediately. The same config in C fails fast with `NET_ERR_INVALID_JSON`. In Go it silently gets the defaults, so a config meant to disable heartbeats looks like it worked.
- **Fix sketch:** Move the zero check into `MeshNodeConfig` (for example, have `MeshNode::new` reject a zero interval or timeout) so every surface inherits it. In Go, make the fields `*uint64` or document that 0 means default.

### [medium] Node and Python `serve_enrollment_auto` also open auto-renewal, which Rust's function of the same name does not; and auto-admit is the only enrollment mode outside Rust
- **Where:** Node `bindings/node/src/enrollment.rs:711-730` and Python `bindings/python/src/enrollment.rs:642-660` both call `serve_enrollment_auto` **and** `serve_renewal_auto`. Rust `sdk/src/mesh_enroll.rs:200-213` serves only `ENROLLMENT_SERVICE`. Operator-approved `serve_enrollment(.., approver)` exists only in Rust (`sdk/src/mesh_enroll.rs:164-193`).
- **Verdict:** CONFIRMED
- **Problem:** The same verb has a different attack surface per language. A TS or Python operator who calls `serveEnrollmentAuto` / `serve_enrollment_auto` also exposes the renewal RPC with the same grant TTL and depth. A Rust operator gets that only by calling `serve_renewal_auto` explicitly. TS and Python also have no approver-gated mode, so they always run the mode Rust's own docs call "Weaker... a leaked, still valid invite gets its holder *admitted*" (`mesh_enroll.rs:196-199`).
- **Failure scenario:** A Python fleet operator ports a Rust deployment that served join only, with renewal deliberately off so grants simply age out. The ported service now silently renews every non-revoked device's grant for another `grant_ttl`, and there is no way to put a human approval in front of joins.
- **Fix sketch:** Rename the binding verb (for example `serve_device_lifecycle_auto`), or split it into two calls that match Rust. Expose `serve_enrollment(approver)` through the bindings: a JS / Python async callback returning bool, like the existing handler TSFN / PyO3 bridges.

### [medium] Zero and missing values for deadlines and timeouts mean different things per language
- **Where:**
  - Plain nRPC call deadline: Node `bindings/node/src/mesh_rpc.rs:274-275` and Python `bindings/python/src/mesh_rpc.rs:345-349` turn `0` into `Instant::now()`, an immediate timeout. Go / C `bindings/go/rpc-ffi/src/lib.rs:872-875` and `include/net_rpc.h:328` treat `0` as no deadline.
  - Org facade (every language): `0` means a 300 s default (`sdk/src/org/call.rs:165-176`; Node `bindings/node/org.ts:119-123`).
  - Handler timeout: Node `bindings/node/src/mesh_rpc.rs:2040-2043` and Python `bindings/python/src/mesh_rpc.rs:513-517` treat `0` as effectively infinite. Go / C `rpc-ffi/src/lib.rs:1246-1249` and `include/net_rpc.h:687-689` treat `0` as the 60 s default.
  - `wait_for_token`: Python, C and Go treat `0` as a non-blocking poll (`bindings/python/src/cortex.rs:1577-1581`). Node passes `Duration::ZERO` into the full wait path (`bindings/node/src/cortex.rs:1447-1455`), which takes a wait-queue permit and can return `QueueFull`. The Python docstring (`:1563-1567`) claims Node matches it, which is wrong.
- **Verdict:** CONFIRMED
- **Problem:** Zero means four different things across the SDKs for the same concept. Go also maps an already-expired or sub-millisecond `ctx` deadline to `0`, meaning no deadline (`go/mesh_rpc.go:1531-1544`). Only the cancel watcher then stops the call, so it surfaces as `ctx.Err()` rather than a typed timeout.
- **Failure scenario:** A team ports a Go service whose `ServeOptions{HandlerTimeout: 0}` relied on the 60 s cap to Python, writing `serve(..., handler_timeout_ms=0)`. The handler is now uncapped, and a stuck handler pins a runtime worker forever. In the other direction, a Python `deadline_ms=0` meaning "no deadline" fails every call instantly.
- **Fix sketch:** Pick one meaning (the C ABI's: 0 = default/none) and normalise Node and Python to it, or reject 0 in Node and Python with a clear error. Correct the Python `wait_for_token` docstring, or add the `0 => poll` branch to Node.

### [low] TS enrollment TTLs are not range-checked, so napi's u32 coercion can mint a 136-year invite
- **Where:** `sdk-ts/src/enrollment.ts:26` re-exports the native class with no wrapper. Natives: `bindings/node/src/enrollment.rs:406-412` (`invite(.., ttl_seconds: u32)`) and `:420-427` (`approve(.., grant_ttl_seconds: u32)`). Core expiry: `sdk/src/enrollment.rs:318` (`now.saturating_add(ttl)`, no cap). The guarded twin is `sdk-ts/src/identity.ts:291-296,401` (`requireIntInRange`).
- **Verdict:** CONFIRMED for the code path. The runtime coercion is napi's documented `ToUint32` behaviour, which the repo's own comment in `identity.ts:291-296` describes ("`2 ** 32` became `0`").
- **Problem:** `identity.ts` guards `issueToken` because napi wraps out-of-range numbers. `enrollment.ts` does not guard `invite` or `approve`. Python rejects negative values (u64 extraction raises). Rust is typed.
- **Failure scenario:** `operator.invite(rv, computeTtl())` where the computation returns `-1` (an off-by-one on an expired window) mints a single-use invite valid for about 2^32 s. Combined with auto-admit (previous finding), a leaked copy admits its holder for over a century. `1.5` becomes `1`, and `2**32` becomes `0` (an invite born expired).
- **Fix sketch:** Wrap `OperatorEnrollment.invite` and `approve` in `sdk-ts` with the existing `requireIntInRange` helper. Also consider a core cap on invite TTL (none exists today on any surface).

### [low] Python `find_nodes_scoped` with no `kind` widens to the whole mesh; Go, C and Node reject it
- **Where:** `bindings/python/src/capabilities.rs:578` (`get_opt_str(d, "kind")?.unwrap_or_else(|| "any".to_string())`). Compare C `src/ffi/mesh.rs:4274-4295` (unknown or empty kind is `InvalidArgument`), Go `go/capabilities.go:228-234` (zero `Kind` = `""`, which C rejects), and Node `bindings/node/src/capabilities.rs:572-573` (`kind: String` is required).
- **Verdict:** CONFIRMED
- **Problem:** The FFI's own rationale is "A narrowing filter that cannot narrow must fail, not widen" (`ffi/mesh.rs:4255-4266`). Python applies it to an empty `tenant`, but a missing `kind` silently becomes `Any`, the broadest filter.
- **Failure scenario:** `mesh.find_nodes_scoped(f, {"tenant": "acme"})`, where the author forgot `"kind": "tenant"`, returns every non-subnet-local provider in the mesh, and the caller picks one. The equivalent `ScopeFilter{Tenant: "acme"}` in Go returns an error. (Scope tags are self-asserted, so this is placement hygiene rather than an auth boundary, hence low.)
- **Fix sketch:** Require `kind` in `scope_filter_from_py`, or fail when `tenant`, `tenants`, `region` or `regions` is present without a matching `kind`.

### [low] Local `TypedChannel.publish` encodes scalars and arrays differently in TS and Python; TS loses the payload
- **Where:** TS `sdk-ts/src/channel.ts:167-172` (`JSON.stringify({...event as object, _channel})`) and `stripChannelTag` at `:104-113`. Python `sdk-py/src/net_sdk/channel.py:96-116,209-211` (wraps as `{"_value": x}`, raises `TypeError` for anything unserialisable).
- **Verdict:** CONFIRMED
- **Problem:** `TypedChannel<T>` has no constraint on `T`. Spreading a number, string or boolean contributes nothing, and spreading an array gives index keys. Python wraps the same values in `_value`. TS `publish` also returns `false` for every ingest error, including a shut-down bus (`bindings/node/src/lib.rs:630-639`), where Python raises.
- **Failure scenario:** `node.channel<number>('metrics/x').publish(42)` stores `{"_channel":"metrics/x"}`, and the subscriber gets `{}` with no error. Python's `publish(42)` stores `{"_value":42,...}`. A mixed-language consumer on a shared adapter (Redis or JetStream) sees three different shapes for the same logical event.
- **Fix sketch:** In TS, either reject non-plain-object events or wrap them as `{_value: x}` to match Python, and unwrap `_value` symmetrically on subscribe in both SDKs.

### [low] Go `RequireSignedCapabilities` cannot be turned off, and its doc states the wrong default
- **Where:** `go/mesh.go:244-246` (`bool` with `omitempty`; comment says "accept unsigned in v1"); FFI doc `src/ffi/mesh.rs:497-499` ("`false` in v1"); core default `src/adapter/net/mesh.rs:3702` (`require_signed_capabilities: true`). Node `bindings/node/src/lib.rs:1773` and Python `:1560` take `Option<bool>` and forward `false`.
- **Verdict:** CONFIRMED
- **Problem:** Go can never send `false`. That is stricter, not fail-open, but the documented default is the opposite of the real one, and the program behaves differently from Node and Python, where `false` is honoured. This is the same bug pattern already fixed for `AutoDirectUpgrade` (`*bool`).
- **Failure scenario:** A Go node configured to accept unsigned announcements from legacy peers silently drops them, while the same config in Python accepts them.
- **Fix sketch:** Change the field to `*bool` and fix both doc comments to say the default is `true`.

### [low] Go reports nRPC cancellation as `RpcKindUnknown` and drops the server status code
- **Where:** `go/mesh_rpc.go:408-421` (no `cancelled` case), acknowledged at `:899-906`. The Rust side emits `"cancelled: ..."` (`bindings/go/rpc-ffi/src/lib.rs:480`). Node and Python give a typed `RpcCancelledError` and a parsed `.status` (`bindings/node/errors.ts:175`, `bindings/python/python/net/mesh_rpc.py:1191`). Go's `RpcError` has only `Kind` and `Message`.
- **Verdict:** CONFIRMED
- **Problem:** A cancel that fires when `ctx` has not been cancelled (for example a mesh-side cancel or teardown) reaches Go callers as `Unknown`. Server status codes (such as the org admission denial `0x0009`) are available to Go only as text inside the message.
- **Failure scenario:** Retry logic written as "retry on Unknown, not on Cancelled" (portable in Node and Python) retries cancelled calls in Go.
- **Fix sketch:** Add `RpcKindCancelled` and a parsed `Status` field. Also list `capability_denied` in `net_rpc.h:54-63`.

### [low] Node `onStreamData` buffers without limit; every other per-stream receiver is bounded and counts drops
- **Where:** `bindings/node/src/lib.rs:2240-2249` (`tsfn.call(.., NonBlocking)`, result discarded; no `max_queue_size` anywhere in `bindings/node/src`). Compare Python `bindings/python/src/lib.rs:2330`, Go `go/stream_inbox.go:35-48,107-114` and Rust `sdk/src/mesh.rs:1375` (bounded inbox plus a `Dropped` counter).
- **Verdict:** PLAUSIBLE. Unverified link: that napi-rs 3.9's default TSFN queue is unbounded (`max_queue_size` defaults to 0, meaning unlimited). If it is instead bounded, events are dropped silently with no counter.
- **Problem:** The same flood from a peer is bounded and counted in Python, Go and Rust, but grows JS heap memory without limit in Node, with no backpressure and no metric.
- **Failure scenario:** A peer streams faster than the JS handler drains, and the Node host's RSS grows until it is OOM-killed.
- **Fix sketch:** Build the TSFN with a bounded queue and count `QueueFull` results as drops, exposed as `subscription.dropped`. Or add a pull inbox to Node to match the other bindings.

### [low] `BlobRef.hash` on a Manifest or Tree ref returns 32 zero bytes in Node and Python, but an error in C and Go
- **Where:** Node `bindings/node/src/blob.rs:314-316` and Python `bindings/python/src/blob.rs:96-98` (`unwrap_or([0; 32])`); C `src/ffi/blob.rs:1504-1510` (`NET_ERR_BLOB_DECODE`), reached from `go/blob.go:550`.
- **Verdict:** CONFIRMED (Python documents it; Node's doc does not mention it)
- **Problem:** Code that keys a cache or dedup table on `ref.hash` collapses every chunked blob onto the all-zero key in JS and Python, while Go fails loudly.
- **Fix sketch:** Return `null` / `None` (or throw) for non-Small refs, matching C and Go.

### [low] The Rust SDK installs no token cache on an identity-less mesh; the bindings always install a fresh one
- **Where:** `sdk/src/mesh.rs:617-619` versus Node `bindings/node/src/lib.rs:1880-1892`, Python `bindings/python/src/lib.rs:1702` and C `src/ffi/mesh.rs:783`.
- **Verdict:** PLAUSIBLE. The rejection behaviour comes from the code comment at `sdk/src/mesh.rs:613-616`; I did not trace it through `can_subscribe`.
- **Problem:** A publisher with an ephemeral identity and a `require_token` channel rejects every subscriber in Rust. The same program in Node, Python or Go verifies subscriber chains against `token_roots` and admits valid ones. This direction fails closed, so the impact is availability or porting surprise only.
- **Fix sketch:** Pick one behaviour. Either always install a cache in the Rust SDK, or make the bindings install the identity's cache (they currently never use the caller identity's `TokenCache`).
